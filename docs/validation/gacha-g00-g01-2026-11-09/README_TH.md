## 1. ทำซ้ำ

Python3.12.14 + NumPy2.3.5 ในผลที่แนบ (เวอร์ชันเต็มในmetadata); Node24.19.0 ใช้ตรวจportของบอร์ดกับbodyต้นฉบับ. ไม่ต้องnpm installหรือimportเกมเพื่อจำลอง. หากใช้เครื่องใหม่ติดตั้งNumPy2.3.5ในenvironmentแยกก่อน

```sh
python docs/validation/gacha-g00-g01-2026-11-09/model.py --self-check
python docs/validation/gacha-g00-g01-2026-11-09/verify.py
python docs/validation/gacha-g00-g01-2026-11-09/model.py --players 4000 --days 365 --seed 20261109 --output /tmp/gacha-g01-reproduce
python docs/validation/gacha-g00-g01-2026-11-09/report.py --input /tmp/gacha-g01-reproduce/results.json --output /tmp/gacha-g01-reproduce/TABLES_TH.md
cmp docs/validation/gacha-g00-g01-2026-11-09/results.json /tmp/gacha-g01-reproduce/results.json
cmp docs/validation/gacha-g00-g01-2026-11-09/summary.csv /tmp/gacha-g01-reproduce/summary.csv
```

33กรณี ×4,000บัญชี ×365วัน seed20261109. `results.json` บันทึกPython/NumPy, sourceSHA, SHA256ของไฟล์โค้ดที่ตรวจและmodel/scenarios. หากเวอร์ชันPythonต่าง `cmp` metadataอาจต่างแม้ผลตัวเลขตรง; เปรียบเทียบส่วนresultsพร้อมhashinputs. modelไม่อ่านเวลาเครื่องและไม่ใช้RNGของruntime. เก็บผลเดิม8พ.ย.ไว้ไม่แก้ เพราะนิยามและสมมติฐานต่างกัน

## 3. นิยามตัวชี้วัดและ censoring

`target_days/sessions` คือครั้งแรกที่มีคนโปรด. `favorite5_sessions` นับจากเริ่มบัญชี; `favorite5_after_acquisition_sessions` รวมvisitที่ได้ตัวเป็นครั้งแรกและนับตั้งแต่นั้น. บัญชีเก่าที่มีเป้าอยู่แล้วบันทึกที่observationแรก (วัน/ครั้ง1) ไม่ตีความว่าเป็นความเร็วรับตัวใหม่. `five_owned`เป็นสมาชิก5; `five_budget_proxy`เป็นมีสมาชิกและกันงบพื้นฐานเท่านั้น

ใช้nearest-rankของ**ประชากรจำลองทั้งหมด**; ไม่เห็นเหตุการณ์ภายใน365วันเป็นright-censored. median/P90/P99ที่อยู่เหนือสัดส่วนสำเร็จเป็นnull/“ยังไม่ถึงในขอบเขต” ไม่เอาเฉพาะผู้สำเร็จมาหาP90. CSVช่องว่างหมายถึงcensored ไม่ใช่0. ผลดิบมีcompleted_pct/censored/horizonทุกevent. P99อยู่ในtailประมาณ40บัญชี ให้ใช้ดูกรณีแย่ ไม่ใช่การันตีทุกคน

`accounts_ore_blocked_pct`นับเคยมีเศษ/dupesพอแต่แร่ไม่พออย่างน้อยหนึ่งจังหวะในโมเดล ไม่ใช่สัดส่วนที่ผู้เล่นจริงกดอัปแล้วติด และไม่ใช่จำนวนvisitที่ขาดแร่

**ถ้านับหลังได้คนโปรดแล้ว** ฐาน80/96อยู่ที่8/9ครั้ง median/P90 แต่ถ้านับจากเริ่มบัญชีคือ11/16. นี่คือประเด็นนิยามOD-07ที่ต้องเลือก ไม่ใช่เหตุให้รายงานเฉพาะตัวเลข8แล้วบอกว่าเป้าผ่าน. ฐานปัจจุบันที่ไม่มีตั๋ว/ฟาร์มอยู่ที่25/40ครั้งภายใต้basketเดียวกัน; โมเดลนี้ไม่รวมตลาด/sidequestทุกทางจึงไม่ใช่เวลาของเกมทุกวิธี

ความต่าง80/100ไม่ได้เปลี่ยนmedianทุกตัวชี้วัด: หลังมีทางเรื่อง/บอร์ดครบ15คนเร็ว ทั้ง15คน★5ของ80/96อยู่ที่152/162วัน เทียบ100/96ที่155/164. การคงเรตเก่า10%+เศษ1–5ลดเหลือ113/117วัน แสดงความเสี่ยงจากรางวัลระหว่างpullมากกว่าดูแต่counter

วันที่28 คนโปรด★5ของฟรี71.62%, +40/30วัน83.8%, +100/30วัน100%; วันที่90จำนวน★5median5/6/8ตามลำดับ. cohortเต็ม15ที่เลือกเก็บมีตั๋ว1,252ใบใน365วันโดยไม่มีbootstrap; แม้growthสมมติ1–2คน/90วัน cohortที่เริ่มเต็มและใช้ตั๋วก็ยังเต็มpoolทั้งหมด ณวัน365. ภายใต้การใช้กลาง100%และoverflowแบบนี้ การเพิ่มตัวช้าเพียงอย่างเดียวไม่แก้สต็อก และไม่ใช่เหตุให้เร่งผลิตตัวหรือยึดสิทธิ์ย้อนหลัง

80เป็นตัวเลือกทดลองที่แนะนำ แต่counterอย่างเดียวไม่ทำให้เป้าOD-07ผ่านสำหรับคนโปรดทุกคน. แยกคนที่มีตั้งแต่เริ่ม/รอรับ/เน้นสะสมก่อน; farm20เป็นปัจจัยสำคัญและยังไม่มีจริง. กรณีthinและแย่งแร่แสดงว่าการมีเศษพอไม่เท่ากับอัปได้. รายงานผลตัวเลขและP90ในTABLES_TH ไม่อ้างเวลาครบ15จากโมเดลเก่าที่ไม่มีทางฟรี/เงินเป็นข้อพิสูจน์รุ่นนี้

80/96ในช่วง10visitแรกอาจได้ผลเหมือนกัน เพราะส่วนต่างงบท้ายรอบ28วันยังมาไม่ถึง. คนเล่น5ครั้งอาจใช้จำนวนvisitมากกว่าคนเล่น3ครั้งแม้ใช้วันน้อยกว่า เพราะweeklyfarmcap4และแจกงานเพียง3visit; ต้องดูทั้งวันและครั้ง ไม่สรุปว่าการเล่นเพิ่มถูกลงโทษจากตัวชี้วัดเดียว

รายเดือนเร่งทรัพยากรและดาวได้จริงในบางช่วง แม้ทุกตัวฟรี. ต้องวัดgapดาว/งบ/บิลด์ที่เวลาเล่นเท่ากันและทดสอบให้มีทางฟรีพอเล่น ไม่เรียกว่า“ไม่มีpaidpowergap”. ไม่สามารถประเมินรายได้ธุรกิจได้เพราะยังไม่มีราคา, purchaseconversion, retention,ต้นทุนผลิตหรือผู้เล่นจริง

ก่อนเปิดจริงต้องมีแหล่งรับเป้าแน่นอน/นโยบาย7–10ครั้ง, งบแจกที่ทำได้จริงใน3visitและไม่พึ่งโหมดที่ยังไม่มี, ทีม5พร้อมitem/tome/บิลด์ที่เล่นจริง, trust/migrationที่เลือกแล้ว และ P09/P04/ledgerผ่าน. รอบนี้เป็นหลักฐานให้ตรวจสเปก ไม่ใช่การอนุญาตเปิดขอบเขตถัดไป
