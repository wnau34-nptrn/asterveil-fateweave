# ตรวจประสิทธิภาพทั้งเกม — 20 พฤศจิกายน 2026

งานนี้มาจากเจ้าของ: “ตรวจสอบอาการดีเลย์ โหลดภาพช้า เดินหน่วงๆ และอื่นๆ ของทั้งเกมเลย และทำการวิเคราะห์หาสาเหตุและเสนอแนะแนวทางแก้ไข ยังไม่ต้องแก้ไขจริง” — **วัดและวิเคราะห์อย่างเดียว ไม่ได้แก้โค้ดเกม** (branch `claude/perf-audit-2026-11-20` มีแค่รายงาน ผลวัด และสคริปต์วัด)

## 0. วัดอย่างไร และข้อจำกัด

- Chromium 1243 ของเครื่อง (Playwright 1.64) แบบ headless, จำลองมือถือ 390×844, `isMobile`, touch, DPR 3, **CPU ช้าลง 4 เท่า** (`Emulation.setCPUThrottlingRate`), เครือข่ายแบบ 4G ใกล้ DevTools “Fast 4G” (9 Mbps ลง, 1.5 Mbps ขึ้น, RTT 150 ms) เฉพาะการทดสอบโหลด
- เกมที่วัด: build แบบ Pages (`vite build --base=/asterveil-fateweave/`) เปิดด้วย `vite preview`; trace/profiler ใช้ `npm run dev` เพื่อให้เห็นชื่อฟังก์ชันจริง (เลขบรรทัดในรายงานแปลงกลับเป็นบรรทัดของซอร์สแล้ว)
- **ไม่ได้วัดบน Pages จริงและ dev API จริง**: นโยบายเครือข่ายของ container นี้ปฏิเสธ `wnau34-nptrn.github.io` และ `asterveil-api-dev.wn-au34.workers.dev` (HTTP 403 จาก proxy) ฝั่งเซิร์ฟเวอร์จึงวัดด้วยโค้ด Worker/Durable Object จริงที่รันในเครื่อง (แบบเดียวกับ `tests/browser/server-play.spec.ts`) บวกดีเลย์เครือข่าย 150 ms และ 300 ms ต่อคำขอ (ตัวเลขเดิมจาก runner ของ GitHub ใน [PERF_P09_02F_TH.md](../../design/p09/PERF_P09_02F_TH.md): คำสั่ง p50 151 ms) ได้สร้าง environment ส่วนตัว `asterveil-fateweave` ที่อนุญาตสองโฮสต์นี้ไว้แล้ว แต่ session นี้ย้ายไปใช้ไม่ได้ ถ้าเปิด session ใหม่บน environment นั้นจะวัดของจริงซ้ำได้ด้วยสคริปต์เดิม (`PERF_URL=…`)
- headless Chromium วาด WebGL ด้วย SwiftShader (ซอฟต์แวร์บน CPU) ตัวเลข FPS ในศึกจึง**แย่กว่ามือถือจริงที่มี GPU** ใช้เทียบกันเองและชี้จุด ไม่ใช่ค่าจริงบนเครื่อง
- **นี่คือ Chromium emulation ไม่ใช่ iPhone/Android จริง** ไม่ได้ทดสอบ Safari เลย

สคริปต์: [`scripts/audit.perf.ts`](scripts/audit.perf.ts) (โหลด เดิน ศึกต่อกัน camp trace) และ [`scripts/server.perf.ts`](scripts/server.perf.ts) (เดินในโหมด server) รันจากโฟลเดอร์ `scripts/` ด้วย `npx playwright test -c playwright.perf.config.ts` ผลดิบอยู่ใน [`results/`](results/) (trace/cpuprofile ขนาดใหญ่ไม่ได้ commit สร้างใหม่ได้ด้วย `PERF_PROFILE=1`)

## 2. สาเหตุ เรียงตามผลกระทบ

### C1 — หน้าแรกดาวน์โหลดภาพของศึกทั้งหมด 26 MB ทันที (โหลดภาพช้า, ศึกแรกรอนาน) — **ผลกระทบสูงสุด**

- `src/main.ts:35` สร้าง `Phaser.Game` ตอนเปิดเกม และ `BattleScene.preload()` (`src/game/scenes/BattleScene.ts:107-122`) โหลด VFX atlas 13 ไฟล์ (10.8 MB ไฟล์, **74 MiB เมื่อถอดเป็น texture**) + unit sheet 5 แผ่น (6.4 MB, 43 MiB) + ฉาก ruins ทุกครั้ง ไม่ว่าผู้เล่นจะอยู่หน้าชื่อเกม ค่าย หรือแผนที่
- `BattleUI` ถูกสร้างตอนเปิดเกม (`src/main.ts:31`) และวาด HUD ที่ใช้ `icon()` → `skill_icons.webp` ขนาด 1536×4096 (5.8 MB, 24 MiB decoded) ซึ่งเซลล์ 256 px แต่แสดงจริงเพียง ~24–48 px (`src/ui/icons.ts:109-114`)
- บน 4G ทั้งหมดนี้แย่งแบนด์วิดท์กับภาพค่าย/แผนที่และเพลง (bgm 2.1–2.2 MB ต่อเพลง) จึงเสร็จที่ 20–24 วินาที ศึกแรกของเครื่องใหม่ต้องรอ “กำลังเตรียมสนาม…” จนกว่า preload จบ
- long task 580–640 ms ตอนเปิดเกมมาจากการถอดรหัส/อัป texture ใหญ่ (`texImage2D` 1.5 s ใน profile ศึกแรก)

### C2 — แต่ละก้าวบนแผนที่บังคับให้เบราว์เซอร์คำนวณสไตล์/เลย์เอาต์ทั้งหน้า (เดินหน่วง) — สูง

### C3 — โหมด server: ก้าวที่กดระหว่างรอคำตอบถูกเก็บไว้แค่ 1 ก้าว ที่เหลือหาย (เดินหน่วง/เดินไม่ไป บน Pages) — สูง (Pages ใช้โหมด server เป็นค่าเริ่มต้น)

- `src/ui/game-shell.ts:735-749`: ก้าวแรกขยับตัวละครทันที (เดาด้วยกติกาเดียวกัน) แต่ระหว่างรอคำตอบ `if (this.waiting) { … this.nextMove = dir; return; }` เก็บได้ก้าวเดียว (ล่าสุดชนะ) และก้าวถัดไปต้องรอคำตอบก่อนส่ง จึงเดินได้ไม่เกิน ~1 ก้าวต่อ RTT
- ผลวัด: RTT 300 ms กดถี่ 8 ครั้งไปได้ 3 ก้าว, แตะทุก 200 ms ก้าวที่ค้างไว้ขยับช้า 230–290 ms ผู้เล่นรู้สึกว่า “กดแล้วไม่ไป/หน่วงเป็นจังหวะ” ยิ่งเน็ตมือถือในไทยไปถึง Cloudflare ช้าแค่ไหนยิ่งชัด
- คำตอบของเซิร์ฟเวอร์ทำให้ `renderWorld()` ทั้งชุดรันซ้ำอีกรอบ (C2 จึงเกิดสองครั้งต่อก้าวในโหมด server)
- retry: 5 ครั้ง timeout 15 s ต่อครั้ง (`src/platform/server-client.ts:54-55,165-176`) กรณีเน็ตหลุดจริงผู้เล่นอาจรอนานมากก่อนเห็นข้อผิดพลาด (ไม่ได้วัด; เป็นข้อสังเกตจากโค้ด)

### C5 — หน่วยความจำภาพสูงตลอดเวลา (เสี่ยงแท็บถูกปิด/รีโหลดบน iPhone) — กลาง

- texture ที่ Phaser ถือ 150–170 MiB ตั้งแต่ศึกแรกและไม่ลดลง เพราะ atlas หลักทั้ง 13 + unit sheet ไม่เคยถูกปล่อย (ปล่อยเฉพาะ encounter atlas 3 ตัวและ unit pilot ตามที่ออกแบบไว้ — ส่วนนั้นทำงานถูก: ศึก 2–4 ลดเหลือ ~151–154 MiB)
- รูป DOM: portrait atlas 1024×3072 (12 MiB decoded) ใช้แสดงรูปเล็ก ~27 รูปในค่าย, `skill_icons` 24 MiB, ฉากหลังค่าย 2400×1000 สองชั้น (9.2 MiB ต่อชั้น)
- ไม่พบการรั่วชัดเจน: JS heap หลัง GC 12.1 → 12.8 MB ใน 4 ศึก, listener คงที่ (242–251), DOM nodes เพิ่ม 3,047 → 3,393 (+~350) และระหว่างเดินเพิ่ม ~25 nodes/ก้าว ควรดูต่อว่ามีอะไรไม่ถูกลบ (เช่น `step-dust` ถ้า `animationend` ไม่มา)

### C6 — cache ของ asset ไม่มีเวอร์ชันในชื่อไฟล์ — กลาง (ประเมินจากโค้ด ไม่ได้วัดบน Pages)

- JS/CSS มี hash ในชื่อ แต่ atlas/ภาพส่วนใหญ่ใน `public/assets` ไม่มี (`fx/healing_fx.webp`, `art/units_mercs.webp` ฯลฯ; บางไฟล์ใช้ `?v=`) GitHub Pages ตั้ง cache สั้น (ปกติ `max-age=600`) จึงต้องตรวจซ้ำ (304) ~70 คำขอทุกครั้งที่กลับมาเล่นหลัง 10 นาที บน 4G RTT 150 ms คือหลายวินาที และไม่มี service worker
- `dist` 113 MB มีไฟล์ที่ไม่ได้ใช้แล้ว (เช่น `units/lyra_pilot.webp` 3 MB เทียบกับรุ่นที่มี hash) มีผลแค่ขนาด deploy ไม่กระทบผู้เล่น

### C7 — อื่นๆ — ต่ำ

- JS bundle 1.24 MB + Phaser 1.37 MB (gzip 339 + 357 KB) โหลดเสร็จใน ~1 s บน 4G ไม่ใช่คอขวดหลัก
- CSS 317 KB ไฟล์เดียว (gzip 61 KB) ไม่เป็นปัญหา
- แผง `?perf=1` เองใช้ CPU ราว 1.3 s ต่อศึก (`perf-probe.ts:35` วนทุก 100 ms คำนวณ texture และเรียก `getParameter`) ตัวเลขที่เจ้าของวัดบนมือถือด้วยแผงนี้จะแย่กว่าเล่นจริงเล็กน้อย
- Chat เป็น HTTP polling 8 s (เปิดแชต) / 10 s (feed ในค่าย ปิดไว้เป็นค่าเริ่มต้น) ไม่หนัก; ตรวจเวอร์ชันทุก 5 นาที

| R1 | **เลื่อน preload ของศึก**: หน้าชื่อเกม/ค่ายไม่โหลด VFX atlas; โหลดเฉพาะ atlas ที่ทีมและศัตรูของ encounter ใช้ (แบบ `encounterFx()` ที่มีอยู่) เริ่มโหลดล่วงหน้าตอนออกจากค่าย/เข้าแผนที่ ด้วยลำดับต่ำกว่าภาพที่อยู่บนจอ; unit sheet ก็โหลดเฉพาะแผ่นที่ใช้ | ดาวน์โหลดหน้าแรก 26 MB → ~3–5 MB; ภาพค่าย/แผนที่บน 4G ขึ้นเร็วขึ้นมาก; texture ลด ~50–100 MiB | ต้องมีภาพสำรองระหว่างโหลด (มีโค้ด fallback แล้วสำหรับ boss atlas); ต้องรัน presentation-coverage/encounter-budget | กลาง (Opus: ฝั่ง Phaser loading) |
| R2 | **ทำ `skill_icons` ขนาดแสดงจริง** เช่นเซลล์ 64 หรือ 96 px (อีกไฟล์ lossless resize จากต้นฉบับ) และสร้าง HUD ศึกเมื่อเข้าศึกครั้งแรก | 5.8 MB → ~0.4–0.8 MB, decoded 24 → 1.5–3.4 MiB, paint ไอคอนเร็วขึ้นทุกหน้าจอ | ต้องให้เจ้าของดูความคมที่ 390px; อัป `?v=` | เล็ก (Sonnet) |
| R3 | **เลิก forced reflow ต่อก้าว**: รีสตาร์ต animation ด้วย Web Animations API (`el.animate`) หรือสลับชื่อ animation สองชื่อแทน `void offsetWidth`; ย้าย `focus()` ไปเฉพาะเมื่อโฟกัสไม่ได้อยู่ที่ปุ่มเดินแล้ว | ตัดเวลาเฟรม ~60–70 ms/ก้าวที่ CPU 4× | ต่ำ (presentation ล้วน) ต้องตรวจ reduced-motion/คีย์บอร์ด | เล็ก (Sonnet) |
| R4 | **วาดหมอกแบบ incremental**: สร้าง fog cell ครั้งเดียวต่อแผนที่ แล้วเปลี่ยน class/style เฉพาะช่องที่ถูกเปิดใหม่ (หรือวาดหมอกใน canvas เดียว); ข้าม `innerHTML` ของ party/danger/hints/action/pack เมื่อ HTML ไม่เปลี่ยน | ตัด ~20 ms JS + style recalc ~1,300 element ต่อก้าว; รวม R3 คาดว่ากด → เห็นขยับจาก ~150 ms เหลือ ~40–60 ms ที่ CPU 4× | ต่ำ–กลาง ต้องคง fog ถูกต้องตอนโหลดเซฟ/เปลี่ยนแผนที่ | กลาง (Sonnet ทำได้ มีสเปกชัด) |
| R5 | **โหมด server: ส่งก้าวต่อเนื่องได้หลายก้าว** — เก็บคิวก้าวที่เดาแล้วว่าถูก (เช่นสูงสุด 3–4 ก้าว) แสดงผลทันทีทีละก้าว และส่ง pipeline ไปเซิร์ฟเวอร์ตามลำดับ (requestId ต่อเนื่อง) หยุดคิวเมื่อคำตอบเจอศึก/อีเวนต์/ต่างจากที่เดา แล้วย้อนตัวละครไปตำแหน่งจริง; หรือคำสั่ง `move` แบบหลายทิศในคำขอเดียว | เดินได้ตามจังหวะนิ้วไม่ขึ้นกับ RTT; ไม่มีก้าวหาย | **สูง**: แตะ protocol P09/ลำดับคำสั่ง/การย้อนเมื่อเจอศึก ต้องคิดเรื่อง D12 และ requestId ใหม่ ต้องมีเทสต์ server-play | ใหญ่ (Opus) |
| R6 | **ศึก: render เฉพาะส่วนที่เปลี่ยน** — `set()` เทียบค่าก่อนเขียน; `render()` ไม่สั่ง `paint()` ทั้งฉากเมื่อไม่ได้มีตัวเพิ่ม/ย้าย (ใช้ `syncBodies` ที่มีอยู่); `placeBackdrop` อ่าน rect ใน rAF ครั้งเดียวหรือผ่าน ResizeObserver | ลดเวลา JS ในศึก ~40–60%, ลดเฟรม > 50 ms | กลาง: ต้องให้ VFX/สถานะตรงกับเหตุการณ์จริงเหมือนเดิม รันเทสต์ presentation/battle | กลาง (Opus วางโครง, Sonnet ทำต่อ) |
| R7 | **ส่ง `battles` memo ให้ `local()` ฝั่งเครื่อง** (`battleMemo()` ตัวเดียวกับ DO) | commit เทิร์นไม่โตตามความยาวศึก (บอสยาว) | ต่ำ: ผลเท่ากันทุกบิตตามเทสต์ `server-perf.test.ts` | เล็ก (Opus เพราะแตะชั้นคำสั่ง) |
| R8 | **cache ระยะยาว**: ใส่ hash ในชื่อไฟล์ atlas/ภาพ (ผ่าน Vite import หรือ manifest) และพิจารณา service worker cache ภาพหลังโหลดครั้งแรก | กลับมาเล่นแทบไม่ต้องโหลดภาพ ไม่ต้องรอ 304 หลายสิบครั้ง | กลาง: SW ต้องจัดการอัปเดตเวอร์ชันให้ถูก (มี update banner แล้ว) | กลาง |
| R9 | ลด CSS animation ที่วนตลอดบนแผนที่/ค่ายเมื่อไม่อยู่ในจอ และเช็ก `backdrop-filter` 8 จุดบนมือถือจริง | ลด paint/แบตบนมือถือ | ต่ำ | เล็ก |
| R10 | ใช้ portrait รูปเล็ก (atlas ขนาดแสดงจริง) ใน DOM แทน atlas 1024×3072 | ลด decoded image memory ~20–30 MiB ในค่าย | ต่ำ ต้องให้เจ้าของดูภาพ | เล็ก–กลาง |
| R11 | ลด retry/timeout ของคำสั่งที่ผู้เล่นกำลังรอ (เช่น timeout 6–8 s, 3 ครั้ง) และให้ป้าย “กำลังเชื่อมต่อ” ชัดเร็วขึ้น | กรณีเน็ตหลุดไม่ค้างนาน | กลาง: ต้องคง idempotency/requestId เดิม | เล็ก |

ลำดับที่แนะนำ: **R1 + R2** (โหลดภาพช้า/ศึกแรกรอนาน, ได้ผลมากสุด) → **R3 + R4** (เดินหน่วงในทุกโหมด, เสี่ยงต่ำ) → **R5** (เดินหน่วงบน Pages, งานใหญ่) → R6/R7 (ศึก) → R8 (กลับมาเล่น) → ที่เหลือ

## 4. ที่ยังไม่ได้ตรวจ

- Pages และ dev API จริงจากเน็ตมือถือในไทย (container ถูกบล็อก) — ควรวัดใน session บน environment `asterveil-fateweave` หรือให้เจ้าของเปิด `?perf=1` บนมือถือตาม [MOBILE_PERF_TH.md](../w8-field-audit/MOBILE_PERF_TH.md)
- iPhone/Safari และ Android จริง, GPU จริง (FPS ในศึกที่นี่วัดบน SwiftShader)
- ศึกบอสยาวและ World Boss, การเล่นต่อเนื่องหลายสิบศึก, เปิดเกมครั้งที่สอง (warm cache) บน Pages
