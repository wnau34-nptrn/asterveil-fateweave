## 1. วิธีและข้อสมมติ

Monte Carlo 8,000 บัญชีต่อกรณี รวม12กรณี ระยะ365วัน seed20261108; Python/NumPy versionsอยู่ในmetadataของ results.json ใช้ common seedเพื่อเทียบสถานการณ์ ไม่ใช่12กลุ่มข้อมูลผู้เล่นจริงที่เป็นอิสระจากกัน

- รายชื่อคงที่15คน เริ่มมีหนึ่งคน★1; กรณีveteranเริ่มมีครบ15คน★3 ไม่มีตั๋วเริ่มต้น
- ชื่อทุกคนมีโอกาสเท่ากัน ไม่มี rate-up; กรณีหลัก7.5%เป็นตัวเต็ม อีก92.5%เป็นเศษจำนวน1หรือ2เท่ากัน; มีกรณีเทียบ5%/10%และ1–5เศษ
- ตัวซ้ำ20เศษ,ปลดคนที่ยังไม่มีด้วย100,ดาวใช้20/40/60/80;ส่วนเกินของคนที่★5แปลงเป็นเศษกลางมูลค่าเท่ากัน เศษกลางเติมราคาอัปดาวได้100%
- การแลกเลือกคนที่ยังไม่มีก่อน หลังมีครบจึงเลือกคนที่ยังไม่เต็มดาวตามลำดับรายชื่อ; ถ้าเต็มทั้งหมดเก็บแต้มไว้ ไม่บังคับแลกคนเต็มดาวเพื่อเปลี่ยนเป็นเศษ
- แบบจำลองอัปดาว/ปลดคนทันทีเมื่อทรัพยากรพอ เพื่อวัดความเร็วที่ไปถึงได้;เกมจริงต้องมีคำสั่งยืนยันและไม่อัปอัตโนมัติโดยอาศัยรายงานนี้
- ฟาร์ม20เศษต่อครั้งเล่นครั้งแรก4ครั้ง/สัปดาห์ เลือกคนที่มีอยู่และยังไม่เต็ม;ผู้เล่น3ครั้ง/สัปดาห์ฟาร์ม60 คน4หรือ7ครั้งฟาร์ม80โดยไม่ซื้อเพดานเพิ่ม
- กรณีใหม่มีตั๋วเริ่มต้น40ใบ: วันแรก16และวันที่7/14/21/28ครั้งละ6;กรณีเก่า20ใบตามสัดส่วนครึ่งหนึ่ง เป็น schedule สมมติ ไม่ใช่เวลาจบเนื้อเรื่องจริง
- รายได้หมุนเวียนฟรีคิดต่อ28วัน ของซื้อคิดต่อ30วัน แล้วเฉลี่ยเป็นรายวันและปัดสะสมลง ไม่ได้จำลองการซื้อ/รับย้อนหลัง/ทำอีเวนต์ตามวันจริง
- ไม่มีตัวฟรีจากเนื้อเรื่อง/บอร์ด ไม่มีตัวใหม่เข้า ไม่มีpromotion/การพัฒนาหลัง★5; ไม่รวมตั๋วหอถาวร12และแพ็กเริ่มต้น10
- สมมติแร่/ทองและทรัพยากรอัปอื่นเพียงพอ ไม่รวมเวลารอ/พลังงาน/เวลาเล่น PvP หรือหอจริง จึงใช้รายงานนี้รับรองงบกิจกรรม20–30นาทีไม่ได้
- จำลองใช้ตั๋วทั้งหมดแม้เต็มแล้ว เพื่อวัดสต็อกเศษ/แต้มที่อาจเกิด ผู้เล่นจริงอาจหยุดสุ่มและเก็บตั๋วแทน
- การละตัวฟรีทำให้สะสมช้ากว่าจริง แต่การไม่มีคอขวดแร่ทำให้อัปดาวเร็วกว่าเกมที่มีคอขวด จึงไม่ใช่ขอบเขตบน/ล่างของทุกตัวชี้วัด

## 3. ความหมายสำหรับข้อเสนอ

1. แนะนำ80เป็นกรณีหลักเพื่อทดสอบ: ที่งบ96/28วันความถี่แลก1.2ครั้ง เทียบ100แต้มได้0.96ครั้ง; ในชุดควบคุมการใช้100ทำให้ครบ15ช้าลง23วันแต่ทุกคนเต็มดาวช้าลงเพียง2วัน
2. จำนวนตั๋วสูงขึ้นไม่ได้ทำให้กำลังซื้อเท่าเดิมโดยอัตโนมัติ กรณีคงรางวัลเดิมแต่ใช้96ใบทำให้ทุกคนเต็มดาวเหลือ110วัน เทียบกรณีหลัก143วัน; การเปลี่ยน80อย่างเดียวไม่รับรองเศรษฐกิจ
3. แม้ปรับเรต/เศษแล้ว โมเดลหลักยังสะสมครบในประมาณ82วันและทุกคน★5ใน143วัน; rosterคงที่15คนจึงไม่ใช่โมเดลรายได้กาชาตัวซ้ำตลอดปี
4. รายเดือน/แพ็กทำให้ครบเร็วขึ้น ต้องทดสอบส่วนต่างฟรี/จ่ายและคุณค่าหลังเต็ม ไม่ใช้ป้าย“แจกเยอะ”เป็นเกณฑ์ผ่าน
5. คนโปรดตัวแรกในแบบจำลองหลักถึง★5median10ครั้งเล่น ซึ่งขึ้นกับฟาร์ม20และไม่มีคอขวดแร่; นี่ไม่ใช่เหตุให้ลดรางวัลฟาร์มโดยไม่ทบทวนOD-07
6. เรายังไม่ยืนยัน7.5%เป็นเรตใช้งาน: สิบครั้งไม่มีตัวเต็ม≈45.86% ถ้า UI/ผู้เล่นมองว่าได้แต่เศษ ต้องทบทวนและทดลอง;ไม่มีสมมติฐานการันตีสิบครั้งอยู่ในผลตารางนี้
7. ก่อนขายต้องเพิ่มแบบจำลองเวลาเนื้อเรื่อง/บัญชีที่มีตัวอยู่จริง/camp resource budgets/newcontent cadence/hoarding/skip-days และข้อมูลเล่นจริง

## 4. ทำซ้ำและตรวจความถูกต้อง

ต้องมีPython3และNumPy; ไม่เพิ่มNumPyเป็นdependencyของตัวเกม ติดตั้งในenvironmentส่วนตัวตามนโยบายที่ใช้ รายงานนี้ใช้versionที่บันทึกในresults.json

~~~sh
python docs/validation/gacha-economy-80-2026-11-08/model.py --players 8000 --days 365 --output /tmp/gacha-80-reproduction
~~~

scenarios.jsonเป็นรายการพารามิเตอร์ ส่วนผลจะเขียนในoutputที่ระบุเท่านั้น ไม่เขียนwalletหรือเกมเซฟ ใช้seedเดียวแต่เปลี่ยนจำนวนบัญชี/NumPyอาจเปลี่ยนquantileเล็กน้อย การเพิ่มพูล/กำหนดrate-up/เพิ่มguaranteeหรือเปลี่ยนแหล่งแจกต้องจำลองใหม่

ตัวแบบตรวจยอดเศษ/เศษกลางไม่ติดลบและดาว0–5ระหว่างรัน ชุดทบทวนเอกสารตรวจsumงบ96/80,40bootstrap,40/100paid,สูตรmassและโอกาสสิบครั้ง รวมถึงsnapshot monotonic/bounds,ครบครบ100%ก่อนตีความquantile และตรวจว่าไม่มีไฟล์runtimeเปลี่ยน

เครื่องมือนี้ไม่ได้อ้างว่าใช้server RNGจริง ไม่ทดสอบtransaction/auth/payment/migrationของเกม ไม่ใช่การผ่านG03–G07ในแผนพัฒนา
