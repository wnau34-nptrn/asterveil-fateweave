# ข้อเสนอแนะ UX/UI — Asterveil: Fateweave

ตรวจวันที่ 4 พฤศจิกายน 2026 · เป็นรายงานเสนอปรับปรุง ยังไม่แก้เกม

เกมมีภาพและบรรยากาศที่ชัดเจน หน้าต่อสู้บนจอสั้นยังแสดงสนาม ทีม และคำสั่งหลักได้ครบ ส่วนโรงตีเหล็กและอัปดาวมีการตรวจรายการและสรุปทรัพยากรที่ควรรักษาไว้ ปัญหาที่ควรจัดการก่อนคือการจ่ายซ้ำในหน้าสกิล การเข้าถึงคำสั่งหลังเลือกสมาชิก และข้อมูลก่อนออกเดินทางที่ถูกภาพตัวละครทับ จากนั้นจึงปรับโครงหน้าและรายละเอียดภาพให้สม่ำเสมอ

## ฐานและวิธีตรวจ

- ใช้ฐาน `feature/fateweave-initial-prototype` ที่ `b3ad98e950d278b0678cd3a334fad02862e1e891` ซึ่งรวม UXD-06 PR #144 แล้ว ตรวจ remote head ตรงกับ checkout ก่อนเริ่ม

- ตรวจ 390×844 และ 390×650: ค่าย ทีม ตัวละคร สกิล ความถนัด พัฒนา อัปดาว กระเป๋า โรงตีเหล็ก สร้างอาวุธ จ้าง ตลาด ปรุงยา แผนฟาร์ม แผนที่ กระเป๋าระหว่างเดินทาง ต่อสู้และคำอธิบายท่า ส่วนเริ่มเกม/ตั้งชื่อ/บทนำและสรุปเดินทางตรวจตามขนาดที่ระบุในภาพ
- ใช้เซฟทดสอบแยก มีสมาชิก 12 คน ลงสนาม 5 สำรอง 3 มีอุปกรณ์และตำราพร้อมให้ตรวจ ไม่แตะเซฟผู้เล่นจริง ไม่ได้ทดสอบความสมดุลหรือประสบการณ์สะสมทรัพยากรตามธรรมชาติ
- Browser audit 6 สถานการณ์หลักผ่านครบหลังแก้ตัวนำทางในสคริปต์ทดสอบและเพิ่มเวลารอเริ่มหน้า จากนั้น targeted interaction อีก 1 สถานการณ์ผ่าน รวม 7 สถานการณ์ที่มีผลสำเร็จ ไม่ใช่ regression suite ทั้งเกม รอบแรกหน้าค่าย 2 กรณีล้มจากสคริปต์ ไม่ถือเป็นข้อบกพร่องของเกม
- ไม่มีผล Safari/iPhone/Android เครื่องจริง ผู้ใช้จริง โปรแกรมอ่านหน้าจอ การเปิดคีย์บอร์ดบนมือถือ หรือการตรวจ contrast ตาม WCAG แบบครบถ้วน ไม่ทดสอบ desktop/320px/ขยายตัวอักษรใหม่ในการตรวจครั้งนี้
- ไม่พบ `CURRENT_STATE.md` ใน workspace จริง ใช้เอกสาร release และโค้ดฐานข้างต้นประกอบ

## 1. P1 — เพิ่มเลเวลสกิลรับดับเบิลคลิกเป็นการจ่ายสองครั้ง

**พบจริง:** ค่าย → ทีม → เอกิส → สกิล → ดับเบิลคลิก “เพิ่ม Lv” ของตั้งรับหมู่ ใน fixture เริ่ม Lv1 ทอง 600 ตำราปราการเล็ก 10 หลังทำเป็น Lv3 ทอง 587 ตำราเล็ก 4 ข้อมูลนี้อ่านจาก Profile ใน localStorage หลังคำสั่ง ไม่ได้อนุมานจากภาพปุ่ม

ผู้เล่นอาจตั้งใจเพิ่มครั้งเดียว แต่คลิกซ้ำเมื่อไม่แน่ใจว่าปุ่มตอบสนองหรือยัง ปัจจุบัน `character-panel.ts` ส่ง `skill-level` ตรงไปยัง host และปุ่มใหม่ยังทำรายการถัดไปได้ ไม่มีขั้นตรวจรายการแบบงานโรงตีเหล็ก/อัปดาว นี่เป็นความเสี่ยงที่ยืนยันบน Chromium automation ไม่ได้อ้างว่าเกิดกับ double-tap ทุกเครื่อง

**เสนอ:** ให้เลือกสกิลและ Lv เป้าหมาย ตรวจผลต่างตามระบบจริง พร้อมตาราง มี/ใช้/หลังทำ แล้วจึงยืนยันครั้งเดียว ใช้ review identity, eligibility check, ป้องกัน stale/repeat confirm และ receipt จาก event/Profile หลัง persist ตามรูปแบบที่มีแล้ว ไม่เปลี่ยนราคาหรือสูตรสกิล

**เกณฑ์รับงาน:** ยืนยันซ้ำ/held Enter ไม่จ่ายครั้งที่สอง, ยกเลิกไม่เปลี่ยนเซฟ, ข้อมูลเก่าต้องตรวจใหม่, แสดง Lv และยอดที่บันทึกจริง งานนี้ควรนำเข้าแผน UXD-07 ก่อนรายละเอียดตกแต่ง

หลักฐาน: [ผล Profile ก่อน–หลัง](interaction-evidence.json), [ภาพหลังดับเบิลคลิก](images/28-skill-after-double-650.png); โค้ด `src/ui/character-panel.ts` handler `skill-level` และ `src/ui/character-view.ts` ฟังก์ชัน `skillLevelRow`

## 2. P1 — เลือกสมาชิกแล้วคำสั่งจัดการอยู่ไกลจากจุดที่เลือก

**พบจริง:** หน้าทีมขนาด 390×650 วางบทสนทนา NPC ภารกิจ และเลเวลค่ายก่อนรายชื่อสมาชิก พื้นที่เลื่อนสูง 577px แต่เนื้อหาเริ่มต้น 1516px หลังแตะเอกิส ปุ่มอัปดาวมีตำแหน่งบนสุดประมาณ y=1827px ขณะจอสูงเพียง 650px ยังต้องเลื่อนลงไปหาคำสั่งเอง

นอกจากนี้การแตะการ์ดใช้ทั้งเลือกสมาชิกเพื่อจัดการ และย้าย/สลับกับอีกกลุ่ม ผู้เล่นต้องเข้าใจโหมดจากข้อความประกอบและสถานะเลือก ซึ่งมีโอกาสสับสนกับการเปิดรายละเอียด

**เสนอ:** ให้รายชื่อและสถานะทีมมาก่อน ย่อภารกิจเป็นแถบพับได้ เปิดรายละเอียดด้วยคำสั่งชัดเจนบนการ์ด และแยก “จัดตำแหน่ง” เป็นโหมดที่เห็นชัด หลังเลือกควรมีแถบคำสั่งใกล้การ์ดหรือแผงรายละเอียดที่เปิดทันทีและคืนตำแหน่งเดิมเมื่อปิด ไม่จำเป็นต้องเพิ่มอีกหลาย modal ซ้อนกัน

**เกณฑ์รับงาน:** แตะสมาชิกแล้วเห็นชื่อที่เลือกและคำสั่งหลักโดยไม่เลื่อนหารายการท้ายหน้า; สลับคน/กลุ่มไม่สั่งอัปเกรด; Escape และปิดแผงคืน focus/scroll เดิม

หลักฐาน: [หน้าทีม](images/05-team-650.png), [หลังเลือกสมาชิกโดยยังไม่เลื่อน](images/27-team-after-pick-650.png), [ค่าตำแหน่ง](interaction-evidence.json); `src/ui/lobby-ui.ts` เมธอด `pick` คืน focus แบบ `preventScroll`

## 3. P1 — ข้อมูลแผนที่และความพร้อมก่อนออกเดินทางถูกภาพค่ายทับ

**พบจริงจากภาพ:** ชื่อแผนที่ที่เลือกและข้อความทีมพร้อมอยู่บริเวณซ้ายล่างของฉากค่าย มีตัวละคร/อาวุธทับและพื้นหลังหลายสี ปุ่มออกเดินทางเด่นมาก แต่ข้อมูลที่ใช้ตัดสินใจออกเดินทางอ่านยากทั้งสองความสูงที่ตรวจ

**เสนอ:** วางแผ่นข้อมูลทึบหรือโปร่งที่ควบคุม contrast ได้ไว้ติดเหนือปุ่มออกเดินทาง แสดงแผนที่ที่เลือก Lv และจำนวนลงสนาม/สำรอง พร้อมปุ่มเปลี่ยนแผนที่ในกลุ่มเดียวกัน กำหนดพื้นที่ของฉากและข้อมูลไม่ให้ทับกันเมื่อจอสั้นหรือชื่อยาว

**เกณฑ์รับงาน:** อ่านชื่อแผนที่และทีมก่อนกดออกเดินทางได้ที่ 390×650/844 โดยภาพตกแต่งไม่ทับข้อความ และไม่เปลี่ยนกฎเลือกแผนที่หรือเงื่อนไขออกเดินทาง

หลักฐาน: [ค่าย 390×650](images/04-camp-650.png); `src/ui/lobby-ui.ts` markup `.lobby-trip .trip-head`

## 4. P2 — ภาพสมาชิกที่ค่ายไม่ตรงกับจำนวนลงสนาม

**พบจริง:** fixture ลงสนาม 5 คน ป้ายทีมแสดง 5+3 แต่ภาพรอบกองไฟมี 4 คน โค้ด `lobby-ui.ts` เลือก `p.party.deployed.slice(0, 4)` จึงไม่ได้แสดงทีมครบในกรณีนี้

**เสนอ:** แสดงครบ 5 คนถ้ารักษาพื้นที่อ่านข้อมูลได้ หรือระบุชัดว่าภาพเป็นบางส่วนและมี “+1” ที่เปิดรายชื่อได้ ควรแสดง “ลงสนาม 5 · สำรอง 3” แทนการให้ผู้เล่นตีความ 5+3 เอง

**เกณฑ์รับงาน:** ภาพกับตัวนับไม่สื่อว่าคนที่ห้าหายจากทีม และผู้เล่นตรวจรายชื่อจริงได้โดยตรง

## 5. P2 — สกิล/ความถนัด/พัฒนาแยกตามระบบมากกว่างานที่ผู้เล่นต้องการทำ

**พบจริง:** หน้าตัวละครมี 5 แท็บ สกิลแสดงรายละเอียดหลายย่อหน้าและเพิ่ม Lv แต่การปลด/ติดตั้งสกิลอยู่ในความถนัด ส่วนพัฒนาเป็นอัปดาว ที่ 390×650 หน้าสกิลมีพื้นที่เลื่อน 422px และเนื้อหา 2030px ต้องผ่านคำอธิบายหลายท่าก่อนถึงตำราค่าย

**เสนอ:** ในงาน UXD-07 ให้มีภาพรวม “สกิลที่ติดตั้ง / เปลี่ยนสกิล / เพิ่ม Lv / เส้นทางความถนัด” ที่เชื่อมกันได้ แยกรายละเอียดท่ายาวเป็นส่วนขยาย แสดงผลหลัก เป้าหมาย คูลดาวน์และสถานะติดตั้งก่อน พร้อมปุ่มไปยัง node ของสกิลนั้นโดยตรง รักษาชื่อตัวละครและสกิลที่เลือกเมื่อไปกลับ

อย่ารวมทุกเรื่องลงหน้าที่เลื่อนยาวกว่าเดิม การจะลดจำนวนแท็บควรลองต้นแบบกับผู้เล่นก่อน เพราะ 5 แท็บปัจจุบันเป็นช่วงเปลี่ยนผ่านของ UXD-06 อยู่แล้ว

**เกณฑ์รับงาน:** ค้นหา เปลี่ยน และเพิ่ม Lv ของสกิลเดียวกันได้ต่อเนื่อง โดยไม่ต้องจำว่าส่วนใดอยู่แท็บไหน; ค่าพื้นฐานยังแยกจากผลจริงตามเงื่อนไขต่อสู้

## 6. P2 — แลกตำราอ่านปลายทางยากและทำรายการทันที

**พบจริง:** ส่วนแลกตำราอยู่ท้ายหน้าสกิล ตัวอย่างปุ่ม “ศัสตราเล็ก 2 → ปราการ 1” ไม่ระบุขนาดปลายทางบนปุ่ม ต้องอ่านหมายเหตุด้านล่างว่าเป็นขนาดเดิม ปุ่มหลายช่องตัดบรรทัด และหมายเหตุ “แลกกลับไม่ได้” อยู่หลังชุดปุ่ม Handler `tome-trade` ส่งคำสั่งตรงเช่นเดียวกับเพิ่ม Lv แต่ครั้งนี้ไม่ได้ทดลองการจ่ายซ้ำของการแลกตำรา

**เสนอ:** ใช้รูปแบบ “ให้: ศัสตราเล็ก ×2 / ได้: ปราการเล็ก ×1” แสดงจำนวนคงเหลือและยอดหลังทำของทั้งสองสาย ย้ายข้อจำกัดแลกกลับไม่ได้ไว้ก่อนยืนยัน ใช้หน้า review ที่อ่านง่ายสำหรับรายการถาวรนี้ และตรวจ/ป้องกันยืนยันซ้ำตามระบบเดียวกับข้อ 1

**เกณฑ์รับงาน:** สายและขนาดต้นทาง/ปลายทางครบทั้งปุ่มและ review, ยกเลิกไม่จ่าย, ไม่สื่อว่ามีการแลกคืนที่ระบบไม่รองรับ

หลักฐาน: [ส่วนแลกตำรา](images/29-tome-trade-650.png); `src/ui/character-view.ts` ฟังก์ชัน `tomeSection`

## 7. P2 — กระเป๋าค่ายให้น้ำหนักงานรีไซเคิลก่อนค้นหาอุปกรณ์

**พบจริง:** ที่ 390×650 เนื้อหาบนสุดเป็นเลือกของปลอดภัยทั้งหมด/ล้างที่เลือก/รีไซเคิล ตามด้วยขยายคลัง เปิดหน้าตัวละคร และตัวกรอง รายการอุปกรณ์จริงเพิ่งเริ่มบริเวณขอบล่างจอ fixture 16 ชิ้นมีเนื้อหาทั้งหน้า 4641px

**เสนอ:** เริ่มด้วยค้นหา/กรองและรายการอุปกรณ์ ใช้แถบงาน “ดูและใส่ / จัดการคลัง / รีไซเคิล” ที่เข้าใจง่าย หรือเข้าโหมดเลือกหลายชิ้นเมื่อกดรีไซเคิลแล้ว แสดงจำนวนที่เลือกและปุ่มตรวจรายการแบบติดขอบเฉพาะเมื่อเลือกของ คง UID/Lv/+/lock/ทุนและข้อจำกัดทำลายของเดิมครบ

**เกณฑ์รับงาน:** เปิดกระเป๋าแล้วเห็นอุปกรณ์อย่างน้อยหนึ่งรายการและวิธีกรองในจอสั้น งานทำลายต้องยังมี review และไม่เลือกของเพิ่มเองเมื่อเปลี่ยนตัวกรอง

## 8. P2 — ข้อมูลสำคัญบางส่วนเล็กและมีสถานะหลายความหมายในพื้นที่เดียว

**พบจริง:** HP/อาชีพ/แนวของการ์ดทีมใช้ 11px; ชื่อ node และป้ายเงื่อนไขในต้นไม้ความถนัดมีขนาดเล็ก/สีจาง; คิวต่อสู้ใช้ภาพย่อและตัวเลขแน่น หน้าค่ายใช้ badge สีเดียวกันกับจำนวนทีม สมาชิกที่จ้าง และจำนวนอุปกรณ์ จึงยังไม่ชัดว่าเป็นจำนวนหรือสิ่งที่ต้องจัดการ

**เสนอ:** ทำลำดับตัวอักษรสำหรับชื่อ ค่าหลัก เงื่อนไข และคำอธิบายให้สม่ำเสมอ ใช้ 12–14px เป็นจุดเริ่มทดลองกับข้อความรองบนมือถือ แต่ยอมให้ขยายตามภาษา/ระบบและทดสอบจริง ไม่บังคับลดข้อความเพื่อยัดให้ครบจอ ใช้สีร่วมกับข้อความ/รูปทรง แยก badge จำนวนจากการแจ้งเตือน และเพิ่มพื้นที่แตะของ node โดยคงรายละเอียดที่เลือกให้อ่านง่าย

**เกณฑ์รับงาน:** ตรวจ contrast และพื้นที่แตะจริง ทดสอบตัวอักษร 200%, ชื่อยาว, keyboard และโปรแกรมอ่านหน้าจอ โดยไม่ทำให้คำสั่งหลักหลุดจากจอ ตัวเลขขนาดเล็กเพียงอย่างเดียวยังไม่ใช่ผล WCAG fail จากการตรวจครั้งนี้

## 9. P2 — ชื่อทรัพยากรและข้อมูลบริการควรอยู่ใกล้การตัดสินใจ

**พบจริงจากภาพ:** ทรัพยากรค่ายแสดงไอคอนกับตัวเลขโดยไม่มีชื่อในแถบที่มองเห็น หน้าตลาดและปรุงยาวางบทสนทนา/ภารกิจก่อนรายการซื้อ/ปรุง บางแถวระบุราคาใกล้ปุ่มอยู่แล้ว แต่ยังต้องอ่านหลายบริเวณเพื่อทราบของที่มี ของที่จะได้ และข้อจำกัด เช่น ยาที่พกออกค่ายได้

**เสนอ:** ช่วงเริ่มใช้งานให้ไอคอนคู่ชื่อ และแตะเปิดคำอธิบายได้เมื่อใช้แบบย่อ ย่อบทสนทนา/ภารกิจหลังอ่านครั้งแรกได้ รายการซื้อ/ปรุงใช้รูปแบบเดียวกัน: ได้อะไร ×จำนวน / มีอยู่เท่าไร / ใช้อะไร / ข้อจำกัดที่เกี่ยวข้อง ไม่ต้องเพิ่ม modal ให้ทุกการซื้อเล็กน้อย; เลือกใช้ review ตามต้นทุนและความย้อนกลับได้ของรายการ

**เกณฑ์รับงาน:** รู้ชนิดทรัพยากรและราคาครบก่อนกด ไม่มีการแสดง quota หรือยอดหลังทำที่แต่งขึ้น และไม่เปลี่ยนเพดานพกยา/ราคา/เศรษฐกิจ

## 10. P3 — ทำภาษาภาพของบริการให้เป็นครอบครัวเดียวกัน

**ข้อเสนอด้านออกแบบ:** ภาพค่ายและตัวละครสวยอยู่แล้ว แต่บริการมีรูปแบบกรอบ ระยะห่าง หัวหน้า และปุ่มต่างกัน โรงตีเหล็กมีกรอบทองและ ledger ชัดเจน ขณะที่หน้าทีม/ร้าน/สกิลใช้รายการยาว ความรู้สึกและวิธีอ่านจึงเปลี่ยนเมื่อย้ายงาน

**เสนอ:** กำหนดชุดรูปแบบร่วมสำหรับหัวหน้า/ย้อนกลับ/ปิด, การ์ดรายการ, ปุ่มหลักหนึ่งงานต่อช่วง, ราคาหรือ ledger, สถานะล็อก/ขาด และ receipt ใช้สีน้ำเงินเข้มกับทองเดิม แต่ลดเส้นกรอบและแสงเรืองที่แย่งจุดสนใจ ให้ภาพตกแต่งอยู่หลังลำดับงาน ไม่จำเป็นต้องเปลี่ยน artwork ทั้งเกมหรือออกแบบทุกหน้าใหม่

**เกณฑ์รับงาน:** สร้างต้นแบบ 2–3 หน้าตัวแทนก่อน ตรวจว่าปุ่มหลักและย้อนกลับหาเจอโดยไม่ต้องเรียนรู้รูปแบบใหม่ทุกบริการ แล้วจึงขยายใช้หน้าที่เหลือ

## สิ่งที่ควรรักษา

- ภาพบรรยากาศค่ายและสนามรบ ตัวละครมีเอกลักษณ์ ไม่ควรให้การเพิ่มข้อมูลบดบังสนาม
- โรงตีเหล็กแสดงผลรับประกันแยกจากส่วนสุ่ม ตาราง มี/ใช้/ได้รับ/หลังทำ และตรวจรายการก่อนจ่าย เป็นรูปแบบที่ควรนำไปใช้ในงานพัฒนาสกิล
- Review อัปดาวแสดงสมาชิกและดาวเป้าหมายชัดเจน ตารางวัตถุดิบกับปุ่มยืนยันอยู่ในโครงที่ใช้งานบนจอสั้นได้ รักษา stale/repeat guard และ receipt เดิม
- ต่อสู้ 390×650 ยังแสดงทีมและสามคำสั่งหลัก พร้อมเปิดคำอธิบายท่าได้; สรุปเดินทางมีปุ่มกลับค่ายติดด้านล่าง แม้รายการของยาว
- การถอนตัวจากแผนที่มีขั้นยืนยันอยู่แล้ว ไม่ควรเพิ่มขั้นซ้ำเพียงเพราะทำรูปแบบ review ร่วมกัน

## ลำดับงานที่เสนอ

1. **ความถูกต้องก่อนจ่าย:** แก้การรับคำสั่งซ้ำของสกิล พร้อม review/receipt และการแลกตำราในขอบเขต UXD-07 ที่วางแผนไว้ ประมาณงานระดับกลาง–ใหญ่ เพราะต้องตรวจ Profile/event และทดสอบรายการถาวร
2. **เข้าถึงงานหลัก:** ปรับหน้าทีมให้เลือกแล้วจัดการได้ทันที และย้ายข้อมูลแผนที่ออกจากภาพค่าย ประมาณงานระดับกลาง; จำนวนตัวละครในภาพและคำอธิบาย 5+3 เป็นงานเล็กกว่าถ้าเลือกแสดงจำนวนส่วนที่เหลือ
3. **ลดการเลื่อน:** ปรับสกิล/ความถนัด กระเป๋า และภารกิจ NPC ที่คั่นหน้าบริการ ประมาณงานระดับกลาง–ใหญ่ ควรทำต้นแบบและทดสอบเส้นทางก่อนลงรายละเอียดภาพ
4. **ความสม่ำเสมอและการอ่าน:** ปรับ typography/contrast/ชื่อไอคอน/badge และชุด component ร่วม ประมาณงานระดับกลาง ทำต่อจากโครงหน้าที่นิ่งแล้วเพื่อลดการแก้ซ้ำ

ระดับงานเป็นประมาณการเชิงเปรียบเทียบ ไม่ใช่กำหนดเวลา ยังไม่มีการอนุมัติหรือเริ่ม implementation จากรายงานนี้ และไม่เสนอสูตร สกุลเงิน ราคา RNG สมดุล battle/save rules ใหม่

## วิธีตรวจรอบถัดไปก่อนยืนยันว่าใช้ง่ายขึ้น

ให้ผู้เล่นใหม่และผู้เล่นที่มีเซฟก้าวหน้าลองงานเดียวกัน ได้แก่ เปลี่ยนสมาชิกสำรอง เปิดรายละเอียดคนที่เลือก เปลี่ยนสกิล เพิ่ม Lv เพียงหนึ่งครั้ง แลกตำราให้ได้สาย/ขนาดที่ระบุ ค้นหาและใส่อุปกรณ์ ตรวจแผนที่ก่อนออกเดินทาง และกลับค่ายหลังจบ บันทึกว่าทำสำเร็จเองหรือไม่ จุดที่เลือกผิด จำนวนย้อนกลับ และความเข้าใจเรื่องยอดที่จะจ่าย ไม่กำหนดตัวเลขผลสำเร็จขึ้นเองล่วงหน้าเป็นผลที่ตรวจแล้ว

ทำ browser regression ที่ 390×650/844, 320×568 และ desktop พร้อมตัวอักษร 200%/safe area/focus/Escape และตรวจ Safari บน iPhone จริง โดยเฉพาะ keyboard ตั้งชื่อ, viewport หลังแถบที่อยู่ยุบ, การเลื่อนแผง และการแตะซ้ำ ผลครั้งนี้ยังใช้แทนการตรวจเหล่านั้นไม่ได้
