# P09-01 — บัญชี guest → ผูกบัญชี → กู้คืน → ย้ายเครื่อง → รวมเซฟ

11 พฤศจิกายน 2026 · **เอกสารออกแบบ ยังไม่มีโค้ดบัญชีในเกมหรือ Worker** · ป้าย **[โค้ด]** = ข้อเท็จจริงที่ตรวจจากโค้ดสาขาเกม; **[เสนอ]** = ข้อเสนอที่รอเจ้าของ/งาน P09-02

## 1. สภาพปัจจุบัน [โค้ด]

- เซฟอยู่ใน localStorage คีย์เดียว `asterveil.fateweave.expedition.v1` เขียนทั้งก้อน `{version:58, profile, run}` ครั้งเดียว (`saveGame`) ผ่าน `StoragePort` ที่ฉีดเข้ามา (`src/core/save/expedition-save.ts`)
- โหลดด้วย `parseGame` ซึ่งตรวจรูปแบบ เพดาน และ replay คำสั่งศึกที่ค้าง; โหลดไม่ผ่าน → `loadGame` คืน `undefined` (เกมเริ่มใหม่) แต่ไม่ลบคีย์เดิม; ข้ามขอบ v44 จะสำรองต้นฉบับไว้ที่ `…backup.v<เดิม>`
- ไม่มี account ID, token, device ID หรือ server revision ใด ๆ; Worker `asterveil-api-dev` ตอบแค่ `GET/HEAD /health`

## 2. สถานะบัญชี [เสนอ]

| สถานะ | ความหมาย | เล่นได้ | เซฟคลาวด์ |
|---|---|---|---|
| `local` | ยังไม่สร้างบัญชี (ผู้เล่นเดิมทุกคนเริ่มที่นี่) | ได้ทั้งหมดแบบ offline | ไม่มี |
| `guest` | server ออก `accountId` + device credential ให้เครื่องนี้ ยังไม่มีตัวตนภายนอก | ได้ | มี แต่กู้คืนได้เฉพาะเครื่องนี้หรือด้วยรหัสกู้คืน |
| `linked` | guest ที่ผูกตัวตนภายนอกแล้ว (เช่น Google) | ได้ | มี กู้/ย้ายเครื่องได้ |
| `deleting` | ขอลบบัญชีแล้ว รอช่วงยกเลิก (ร่าง 14 วัน) | ได้แบบ local | หยุดรับเซฟ |
| `suspended` | admin ระงับ (ใช้กับระบบ online ภายหลัง) | ได้แบบ local | อ่านได้ เขียนไม่ได้ |

การเปลี่ยนสถานะ

| จาก → ไป | ทริกเกอร์ | เงื่อนไข/ผลข้างเคียง |
|---|---|---|
| local → guest | ผู้เล่นเปิด “เซฟคลาวด์” (แนะนำชวนหลังเคลียร์ MAP1) | `POST /v1/guest` พร้อม `requestId`; retry ได้ id เดิม → บัญชีเดิม ไม่สร้างซ้ำ; อัปโหลดเซฟ local เป็น revision 1 (`origin=legacy`) |
| guest → linked | ผู้เล่นกด “ผูกบัญชี” | ตรวจ id token ของผู้ให้บริการบน server; ถ้าตัวตนนั้นผูกบัญชีอื่นอยู่แล้ว → **ไม่รวมบัญชี** ให้เลือก “สลับไปบัญชีนั้น” (เข้า §4 เซฟขัดกัน) หรือยกเลิก |
| guest → guest (เครื่องใหม่) | ใส่รหัสกู้คืน | รหัสใช้ครั้งเดียว ออกใหม่ทุกครั้งที่ใช้; เครื่องเก่ายังใช้ได้จนกว่าผู้เล่นเพิกถอน |
| linked → linked (เครื่องใหม่) | เข้าสู่ระบบด้วยตัวตนเดิม | ออก device credential ใหม่ แล้วดึงเซฟ (§4) |
| ใด ๆ → local บนเครื่องนี้ | ออกจากระบบ | ลบ credential ในเครื่อง เซฟ local คงอยู่ เซฟคลาวด์ไม่ถูกแตะ |
| guest/linked → deleting → (ลบ) | ขอลบบัญชี | ต้องยืนยันซ้ำ; ระหว่างรอยกเลิกได้; ลบจริงลบเซฟคลาวด์/ตัวตน เหลือ ledger แบบไม่ระบุตัวตนตามนโยบายความเป็นส่วนตัว (OD-13 ต้องมีก่อนเปิดคนนอก) |

credential [เสนอ]: access token อายุสั้น (ร่าง 15 นาที) + refresh token หมุนเวียน (ร่าง 30 วัน, เก็บแค่ hash บน server) แยกคีย์จากเซฟใน localStorage; การ “ล้างข้อมูลเบราว์เซอร์” ทำให้ guest ที่ไม่มีรหัสกู้คืนหาย → จึงต้องชวนผูกบัญชี/เก็บรหัส

## 3. สถานะการซิงก์ของเครื่อง [เสนอ + โค้ดต้นแบบ]

ต้นแบบ pure TypeScript: `src/core/cloud/cloud-save.ts` (`syncStep`) พร้อมเทสต์ `tests/cloud-save-envelope.test.ts` — ยังไม่ต่อกับเกม

| สถานะ | ความหมาย |
|---|---|
| `guestLocal` | ไม่มีบัญชี: ทุก event ไม่มีผล เล่น local อย่างเดียว |
| `synced` | เซฟ local = revision ล่าสุดที่รู้ |
| `dirty` | มีเซฟ local ใหม่กว่า revision ที่ซิงก์ |
| `uploading` | ส่งคำขออยู่ (มี `requestId`, จำนวนครั้ง) |
| `waiting` | ออฟไลน์/หมดเวลา: รอส่งซ้ำ **ด้วย requestId เดิม** |
| `conflict` | server มี revision ใหม่กว่าที่เครื่องอ้าง: รอผู้เล่นเลือก ไม่ส่งต่อเอง |
| `blocked` | ถูกปฏิเสธ/รูปแบบเซฟของ server ใหม่กว่าเกมนี้/ออกจากระบบ: หยุดซิงก์ แต่เล่น local ได้ |

กรณีขอบ

- **ออฟไลน์**: เล่นต่อ เซฟ local ตามเดิม; สถานะเป็น `dirty`/`waiting` และส่งเมื่อกลับมาออนไลน์ ฟีเจอร์ที่ server เป็นเจ้าของ (รางวัลรายวัน กาชา ฯลฯ ในอนาคต) ปิดชั่วคราว
- **หมดเวลา**: ไม่รู้ว่า server commit แล้วหรือยัง → ส่งซ้ำด้วย `requestId` เดิม server ตอบผลเดิม (`replayed`) ไม่เขียนซ้ำ; ครบ 5 ครั้ง (ร่าง) หยุดรอจนผู้เล่นสั่งหรือเครือข่ายกลับ
- **ส่งคำสั่งซ้ำ / กดสองที**: requestId เดิม payload เดิม → คำตอบเดิม; requestId เดิม payload ต่าง → ปฏิเสธ `requestReused`
- **เซฟระหว่างอัปโหลด**: คำขอที่ค้างใช้ payload เดิม เซฟใหม่ถูกจดเป็น `pending` แล้วตามไปทีหลัง ไม่หาย
- **สองเครื่องเล่นพร้อมกัน**: server ใช้ compare-and-swap บน revision; เครื่องที่ช้ากว่าได้ `conflict`

## 4. ย้ายเครื่องและเซฟขัดกัน [เสนอ]

หลัก: **ไม่รวมเซฟแบบรายช่อง** เพราะ profile ต้องสอดคล้องทั้งก้อน (ของ UID, ทีม, ศึกที่ค้าง ตรวจด้วย replay) การรวมสองก้อนเสี่ยงของซ้ำ/ของหาย และเปิดช่องปั๊มยอด

| กรณีบนเครื่องที่เพิ่งเข้าสู่ระบบ | ผล |
|---|---|
| ไม่มีเซฟ local | ดึงเซฟคลาวด์มาเล่นเลย |
| มี local แต่คลาวด์ว่าง | อัปโหลด local เป็น revision 1 |
| local = คลาวด์ (digest เท่ากัน) | `synced` |
| local มาจาก revision เดียวกับคลาวด์และแก้ต่อ (base ตรง) | อัปโหลดตามปกติ |
| ทั้งสองต่างกันและ base ไม่ตรง | หน้าเลือก: แสดงสรุปทั้งสองฝั่ง (ระดับค่าย จำนวนสมาชิก แผนที่ที่เคลียร์ เวลาที่ server บันทึก) ให้เลือก **ทั้งก้อน** |

ฝั่งที่ไม่ถูกเลือก **ไม่ถูกลบ**: local เก็บเป็น `…backup.cloud.<revision>` ในเครื่อง; คลาวด์เก็บเป็นประวัติ revision เดิม (ร่าง 10 ก้อนล่าสุด + 30 วัน) กู้คืนทาง support/admin ได้

เลือก “ใช้ของเครื่องนี้” = อัปโหลดทับโดยอ้าง base เป็น revision ล่าสุดของ server (เป็น revision ใหม่ ไม่ทำลายประวัติ). เลือก “ใช้ของคลาวด์” = สำรอง local ก่อน แล้วเขียนเซฟคลาวด์ลง local
