# P09-01 — Server เป็นผู้ตัดสินทั้งหมด (D10 = ค)

11 พฤศจิกายน 2026 · เจ้าของเลือกด้วยคำว่า “เลือก ค.” ต่อคำถามว่าจะให้ server ตัดสินทุกอย่าง (ปลอดภัยสูงสุด เล่น offline ไม่ได้) · **[โค้ด]** = ข้อเท็จจริง; **[เสนอ]** = ข้อเสนอ · ยังไม่ deploy ไม่สร้าง D1/DO ไม่แก้เซฟ v58

## 1. ผลของการเลือก

- สถานะเกมตัวจริง (profile + การเดินทาง + ศึกที่ค้าง) อยู่บน server เท่านั้น เครื่องเป็น “หน้าจอ”: ส่ง**คำสั่ง** ได้**ผลลัพธ์**กลับ
- แก้ทอง/แร่/ตรา/ดาว/ของ/สเตตัส/ผลกาชา/ดาเมจในเครื่อง ไม่มีผล เพราะ server ไม่รับตัวเลขจากเครื่อง
- เล่น offline ไม่ได้: หลุดเน็ต → หยุดรอเชื่อมต่อ สถานะบน server ไม่หาย ศึกที่ค้างเล่นต่อได้
- ต้องมีบัญชีตั้งแต่เปิดเกม (สร้าง guest ให้อัตโนมัติ แล้วชวนผูกบัญชี)
- ข้อเสนอเดิมที่ถูกแทน: “PvE เชื่อเครื่อง”, การอัปโหลดเซฟทั้งก้อนเป็นประจำ, สถานะซิงก์ offline และหน้าเลือกเซฟเมื่อขัดกัน (ไม่มีสองฉบับให้ขัดกันอีก)

## 2. ข้อเท็จจริงที่ทำให้ทางนี้ทำได้ [โค้ด]

- กฎต่อสู้ `src/core/battle` เป็น pure/deterministic ไม่มีสุ่มหรือนาฬิกา คำสั่งศึก (`Command`) serialize ได้อยู่แล้วและเซฟ replay ได้ → รันบน server ด้วยโค้ดชุดเดียวกัน
- `core/world` และ `core/save` เป็น pure ไม่ import browser/Phaser; `parseGame` ≈ 0.7 ms ต่อเซฟเล็ก
- **ช่องโหว่ปัจจุบันที่ต้องปิด**: seed ถูกสร้างบนเครื่อง (`freshSeed()` ใน `src/ui/game-shell.ts` ใช้ `Date.now()` กับ `Math.random()`) และ seed ใช้กำหนดศัตรูบนแผนที่ (`core/world/world.ts`), กระดานจ้าง (`profile.ts`) และการหลอม (`forge.ts`); ใครรู้ seed ทำนายหรือเลือกผลสุ่มได้
- UI เรียกฟังก์ชันใน `core/world` แล้วแก้ `Game` ในเครื่องตรง ๆ แล้ว `saveGame` — ยังไม่มีชั้น “คำสั่งค่าย” ที่ serialize ได้ (มีแค่คำสั่งศึก) งานนี้จึงใหญ่

## 3. สถาปัตยกรรม [เสนอ]

```
เครื่อง (Pages)                         Cloudflare
  UI + Phaser (แสดงผล, preview ศึก)      Worker: auth, routing, rate limit
  ส่ง {requestId, seq, kind, args}  ──►  Durable Object 1 ตัว/บัญชี
  ◄── ผลลัพธ์ + มุมมองสถานะ (ไม่มี seed)     - ถือสถานะใน memory, ทำคำสั่งทีละคำสั่งตาม seq
                                           - ใช้ core/world + core/battle ชุดเดียวกับเกม
                                           - เขียน snapshot + command log ลง storage ของ DO
                                         D1: บัญชี/ตัวตน/ledger/ประวัติ/admin
```

- **ลำดับและคำสั่งซ้ำ**: ทุกคำสั่งมี `seq` = ลำดับถัดไปของบัญชี และ `requestId`; ต้นแบบ `decideCommand` ใน `src/core/cloud/cloud-save.ts` (apply / replayed / requestReused / stale / gap / invalid)
- **หมดเวลา**: ส่งซ้ำ `requestId`+`seq` เดิม → ได้ผลเดิม ไม่ทำซ้ำ
- **สุ่ม**: seed สร้างและเก็บบน server เท่านั้น ไม่ส่งให้เครื่อง; เครื่องรู้แค่ผล (ศัตรูที่เจอ ของที่หลอมได้ กระดานจ้าง ผลกาชา)
- **มุมมองเครื่อง**: server ส่งสถานะที่ตัด seed/ข้อมูลอนาคตออก; ฟังก์ชันที่ UI ใช้คำนวณแสดงผลต้องไม่ต้องการ seed (ต้องสำรวจใน P09-02)
- **ความหน่วง**: preview ศึกยังคำนวณในเครื่องได้ทันที (ไม่ใช้สุ่ม) แต่การยืนยันคำสั่ง/การเดินหนึ่งช่องต้องรอ server หนึ่งรอบ (เป้าหมาย < 200 ms) ระหว่างรอล็อกปุ่มแบบเดียวกับ presentation lock ที่มีอยู่
- **หลายเครื่อง**: เล่นได้ทีละเครื่องต่อบัญชี เครื่องที่เข้าใหม่ได้สิทธิ์ เครื่องเก่าแสดง “กำลังเล่นบนอุปกรณ์อื่น” (D12)
- **เซฟในเครื่อง**: คีย์เดิม `asterveil.fateweave.expedition.v1` ไม่ถูกลบ ใช้เป็นต้นทางนำเข้าครั้งเดียว (D11) และเป็นสำรอง; ไม่ใช้ตัดสินอะไรอีก
- **ย้ายเวอร์ชันเซฟ**: snapshot บน server ใช้รูปแบบเซฟเดิม (`{version, profile, run}`) ย้ายด้วย `parseGame` ตอน DO โหลด แล้วเขียนเวอร์ชันใหม่ — เส้นทางเดียวกับ local วันนี้
- **admin**: ดู/ย้อน snapshot, ให้/ยึดของผ่าน ledger พร้อม `admin_audit` (OD-13)

## 4. ความเสี่ยงที่ยังเหลือ

- บอท/สคริปต์กดแทนคน (เล่นตามกฎ แต่เร็วผิดปกติ) → rate limit + telemetry
- บั๊กในกฎเองถูกใช้ประโยชน์ → แก้กฎ + ย้อนด้วย ledger/snapshot
- server ล่ม = เล่นไม่ได้ทุกคน → ต้องมี status/ประกาศ และแผน rollback
- ค่า server: คำสั่งศึก/เดินเป็นงาน CPU ระดับ ms แต่จำนวนคำขอมากกว่าแบบซิงก์เซฟมาก → วัดใน P09-02 และตรวจราคา Workers/DO ปัจจุบัน

## 5. ลำดับงานที่เสนอ (แทนแผนซิงก์เซฟเดิม)

1. **P09-02a** ชั้นคำสั่ง: ทำทุกการกระทำของค่าย/แผนที่ให้เป็นคำสั่ง serialize ได้ (แบบเดียวกับคำสั่งศึก) + ตัวประมวลผล pure `applyCommand(state, cmd)` + เทสต์ว่าผลเท่ากับการเรียกฟังก์ชันเดิม; ย้ายการสร้าง seed ออกจาก UI; ยังเล่น local ได้เหมือนเดิมในขั้นนี้
2. **P09-02b** Worker + DO + D1 (ต้องมีสิทธิ์ D1 Edit/DO จากเจ้าของ): auth guest/link, คำสั่งผ่าน DO, snapshot/log, นำเข้าเซฟเดิม (D11)
3. **P09-02c** ต่อ UI กับ server: ล็อกระหว่างรอ, reconnect, “เล่นบนอุปกรณ์อื่น”, ตัดโหมด local ตอนเปิดใช้จริง
4. telemetry/feedback/admin ตาม OD-13 แล้วจึง P04
