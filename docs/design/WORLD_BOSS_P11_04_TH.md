## MVP ที่เลือก (เล็กที่สุดที่ครบข้อกำหนดเดิม)

- **บอสสัปดาห์ละหนึ่งตัว** (สัปดาห์ = `weekOf` เริ่มวันจันทร์ 00:00 เวลาไทยบน server) ใช้ผู้คุมรอยแยกชุดพิเศษ `world-boss-warden` (HP 2400 ต่อครั้ง ล้มไม่ได้ในแปดรอบ เฟส 70%/35% เดิมยังเกิดในศึก)
- **เข้าสู้จากค่ายด้วยทีมสนามของตัวเอง** HP เต็ม ไม่มีความล้า ตำแหน่งตามแถวที่ตั้งไว้ · **ครั้งละไม่เกิน 8 รอบ**
- **สัปดาห์ละ 5 ครั้ง** (ไม่ใช่วันละ 3 ตามร่างเดิม): OD-06 เล่น 3–5 ครั้ง/สัปดาห์ ไม่มีภาระรายวัน — เป็นทางเลือก "สิทธิ์สะสมต่อกิจกรรม" ที่เอกสารเดิมเปิดไว้
- **ผลงาน = HP ของตัวบอสที่ลดจริงในศึกนั้น** (ไม่นับลูกน้อง ไม่นับรักษา/โล่) ศึกต้องจบจริง (ชนะ/แพ้/ครบ 8 รอบ) และบอสต้องเสีย HP อย่างน้อย 1 จึงนับ (`unfinished`/`noDamage` ไม่เสียสิทธิ์)
- **ไม่มีกวาดล้าง World Boss** และไม่มีโหมดฝึกแยก (ออฟไลน์เล่นได้ตามกฎเดียวกันแต่ไม่มี HP ส่วนกลาง)

## ทำไมไม่ต้องมี "เริ่ม attempt" แยก

ศึกของ Fateweave ไม่มีสุ่ม (เจตนาประกาศล่วงหน้า resolver deterministic ไม่มี seed) ศึกบอสโลกจึงไม่มีอะไรให้ "สุ่มใหม่":
เครื่องเล่นทั้งศึกเอง (preview ใช้ resolver เดียวกัน) แล้วส่ง **คำสั่งเดียว** `worldBoss { attempt, commands }` ที่มีทุกเทิร์น
server เล่นซ้ำจากทีมในเกมของ server เอง (snapshot ทีม/อุปกรณ์ = เกมที่ seq นั้น ซึ่ง log เก็บไว้แล้ว) จึงไม่เชื่อดาเมจจากเครื่อง

- `attempt` = ครั้งที่ของสัปดาห์ (+1) → ส่งซ้ำด้วย request ใหม่ได้ `stale`, retry requestId เดิมได้คำตอบเดิม (book) แม้ข้ามสัปดาห์
- หลุดก่อนส่ง = ยังไม่ใช้สิทธิ์ ส่งใหม่ได้ (ไม่มีหน้าต่างหมดอายุให้หลุด) · ผลศึกเดิมทุกครั้ง จึงลองใหม่ไม่ได้อะไร "ฟรี"
- ข้อจำกัดที่ยอมรับ: เครื่องวางแผนเทิร์นที่ดีที่สุดก่อนส่งได้ (เหมือนเล่นด่านปกติ) ดาเมจต่อครั้งมีเพดาน = HP ชุดบอส และรางวัลส่วนตัวไม่ขึ้นกับดาเมจ
- เฟสส่วนกลาง: รุ่นนี้ไม่มี (HP ส่วนกลางไม่เปลี่ยนกฎในศึก) จึงไม่ต้องมี phaseSnapshot

## HP ส่วนกลาง

- `sharedHpFor`: กำหนดตอนสัปดาห์เปิดครั้งแรก = บัญชีที่เข้าร่วมสัปดาห์ก่อน × 2500 ภายใน [5000, 5,000,000] ไม่เพิ่มกลางสัปดาห์ (5000 ≈ ผู้เล่นแข็งสองคนเต็มสิทธิ์ → server เล็กยังถึง milestone ได้)
- Durable Object ใหม่ `WorldBoss` (ชื่อ `world-boss` ตัวเดียว, SQLite ใน DO ไม่ใช่ D1): ตาราง `weeks` (hp, left, accounts) และ `hits` (id PK = `<account>:w<week>:a<n>`)
- รับ hit ครั้งเดียว ตัด HP ได้ไม่เกินที่เหลือ (`applied`) → ตายพร้อมกันหลายคนไม่ต่ำกว่า 0 · สัปดาห์ที่ปิดแล้วตอบรับแต่ไม่หัก · ไม่นำ overkill ไปบอสตัวถัดไป
- load probe (ตอน 2): ~0.1 ms/hit ในหน่วยความจำ, 10,000 hit/สัปดาห์ ≈ 1 วินาที CPU → DO เดียวพอสำหรับช่วงทดสอบ (ยังไม่ได้วัดบน Cloudflare จริง)

## ลำดับบน server (ไม่ต้อง transaction ข้าม DO)

1. Worker ส่ง `worldBoss` ไป DO ของบัญชี → resolver เล่นซ้ำ → เกม/log/`reward_ledger`(`wb:w<สัปดาห์>:a<n>`, `wb:w<สัปดาห์>:p-2`…)/**outbox** `wb_hits` บันทึกใน transaction เดียว
2. ทุกคำตอบของ DO บัญชีแนบ hit ที่ยังค้าง (header ภายใน) → Worker ส่งให้ `WorldBoss /contribute` → แจ้งกลับ `/hits/taken` · ล้มกลางทางก็ส่งใหม่กับคำตอบถัดไป (`/v1/state`, `/v1/session`, คำสั่งถัดไป) ได้ผลเดิม
3. `claimWorldBoss { id, week }`: Worker อ่าน `{week, hp, left}` ของสัปดาห์นั้นจาก `WorldBoss` ส่งเข้า context; log เก็บค่า (`boss`) ไว้ให้ `/verify` เล่นซ้ำได้ตรง
4. `GET /v1/worldboss`: HP ส่วนกลางสัปดาห์นี้/สัปดาห์ก่อน สำหรับหน้าจอ (ตอน 2)

ออฟไลน์: คำสั่งเดียวกันใช้วันของเครื่อง (ได้รางวัลเข้าร่วม/ส่วนตัวเหมือนกวาดล้าง/บอร์ด) ส่วนรวมถูกปฏิเสธ `offline` · ออนไลน์ server ประทับวันเอง ปฏิเสธ `day` ของเครื่อง
