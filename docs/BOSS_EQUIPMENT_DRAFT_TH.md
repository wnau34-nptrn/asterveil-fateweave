## 1. ฐานระบบที่ตรวจเมื่อเริ่มพัฒนา

- บอส `rift-warden` / ผู้คุมรอยแยก อยู่บทแรก ต่อสู้และดรอปที่ Lv11; ปัจจุบันให้อุปกรณ์ปกติสามชิ้น โอกาสสีฟ้า/ม่วง/ทอง 20/45/35 และสุ่มได้ทุกเซ็ต
- เครื่องประดับ `charm` ใส่ได้ทุกอาชีพ มีหนึ่งช่องต่อคน ค่าสถานะหลักเป็น Support; Lv11 คุณภาพ 100% / +0 ให้ Support 18% ไม่เพิ่ม Attack โดยตรง
- ของสีทองมีสาม affixes และหนึ่ง special ทั่วไป (`laststand`, `markhunter`, `renewal`); ขณะนี้ไม่มี unique identity หรือ special เฉพาะบอส
- Affixes เครื่องประดับที่กติกาปัจจุบันยอมรับ: Support, Attack, Luck, SPD, Leech, HP; ห้ามใส่ Armour/Resistance เป็น affix เครื่องประดับโดยอ้างว่าเป็นระบบเดิม
- เพดานอัปเลเวลอุปกรณ์ถาวรปัจจุบันสูงสุด Lv10 แต่ของดรอป Lv11 ใช้ได้ตามเดิม ไม่ลด Lv ไม่เปิดเพดานใหม่ในงานนี้
- ระบบหาอาวุธนับจำนวนอุปกรณ์ปกติที่ดรอป มีตัวนับรายอาชีพ ต้องแยกจากตัวนับบอส
- ปัจจุบัน Hero ทำดาเมจโดยไม่มีเกราะของ Enemy มาลด; เกราะ/ต้านพลังงานใช้ลดดาเมจที่ Hero รับ จึงไม่แสดงคำอ้าง “ดาเมจหลังเกราะศัตรู”

แหล่งอ้างอิงใน repository: `src/content/world/chapter1.ts`, `src/content/encounters/catalog.ts`, `src/core/world/types.ts`, `src/core/world/equipment.ts`, `src/core/world/targeted-loot.ts`, `src/core/battle/engine.ts`, `src/ui/character-metrics.ts` เป็นหลัก เอกสารเก่าที่ระบุ Attack เพิ่มเฉพาะโจมตีปกติมีบริบทประวัติ ต้องอ้างอิง resolver ปัจจุบัน

## 2. ขอบเขตแรกที่แนะนำ

บอสหนึ่งตัว เครื่องประดับสามแบบ ใช้เงินตรา/ช่องสวมใส่/ระบบพัฒนาเดิม ของทุกชิ้นเป็นสีทอง Lv11 / +0 มีโอกาสติดเซ็ตปกติ 60% และมี **พลังบอสหนึ่งอย่างแทน special สีทองทั่วไป** ไม่ได้ทั้งสองแบบพร้อมกัน

เป้าหมายคือทางเลือกจัดทีม ไม่ใช่ของที่ชนะทุกสถานการณ์: ต้องหาเซ็ตให้เข้ากับชุดเดิม เสีย special ทั่วไป และพลังบอสต้องตรงกับสถานการณ์ ของทั่วไปที่คุณภาพ/affixes ดีและครบเซ็ตจึงยังมีเหตุผลให้ฟาร์ม

พลังบอสเป็นเลขคงที่ ไม่สุ่มความแรง ไม่เพิ่มจาก + / Support / Attack / Lv เพื่อไม่คูณพลังหลายชั้น คุณภาพหลักและ affixes ยังสุ่ม 80–120% ตามเดิม ไม่มีระดับสีใหม่ ไม่มีเงินตราใหม่ ไม่มีระบบสะสมพลังถาวร

## 3. อุปกรณ์ที่เสนอ

ตัวเลขทั้งหมดเป็น **ค่าร่างสำหรับนำไปจำลอง** ยังไม่อ้างว่าผ่าน combat balance

| ชิ้น / ID ร่าง | พลังเฉพาะ | เหมาะกับ / ข้อแลกเปลี่ยน |
|---|---|---|
| ตราพิทักษ์ผู้คุม / `warden-aegis` | ครั้งแรกต่อรอบที่ผู้สวมเสีย HP จริงจากการโจมตีโดยตรงของศัตรูและยังยืนอยู่ หลังจบ hit นั้นให้โล่ขั้นต่ำ 6: `barrier = max(barrier, 6)` | ผู้รับการโจมตี/รับแทน; โล่รับ hit ถัดไป ไม่ย้อนลดดาเมจ ไม่กันตาย ไม่เกิดถ้าโล่เดิมรับหมด |
| เศษแกนรอยแยก / `warden-focus` | ครั้งแรกต่อรอบที่ผู้สวมใช้คำสั่งโจมตีปกติหรือสกิลทำดาเมจแบบเลือกศัตรูหนึ่งตัว ใส่เป้าหมายที่ติดตราก่อนโจมตี เพิ่มดาเมจตรง 4 เฉพาะเป้าหมายหลัก | ทีมเล่นตรา; เป้าหมายไม่ติดตราไม่ได้โบนัส ไม่ใช้สิทธิ์กับการติดตราเอง ไม่เพิ่มดาเมจรอง/หมู่/สวนกลับ |
| ประทีปผนึก / `warden-lantern` | ครั้งแรกต่อรอบที่ผู้สวมใช้คำสั่ง `heal` รักษาเพื่อนที่ยังยืนอยู่คนอื่นและฟื้น HP จริง หลังจบผลปกติให้เพื่อนมีโล่ขั้นต่ำ 6: `barrier = max(barrier, 6)` | Priest ที่รักษาเป็นรายคน; ไม่เกิดจากรักษาตัวเอง/HP เต็ม/Prayer/เพลง/ดูดเลือด/ฟื้นอัตโนมัติ ไม่เพิ่มโล่ที่สูงกว่าอยู่แล้ว |

ทุกชิ้นสวมได้ทุกอาชีพ แต่ต้องบอกอย่างชัดเจนเมื่ออาชีพนั้นไม่มีคำสั่งใช้เงื่อนไข เช่น Lyra ใส่ประทีปได้แต่ไม่มี Heal ไม่บังคับให้ทุกชิ้นทำงานกับทุกอาชีพ และไม่เปลี่ยนอาชีพเพื่อแก้ความเข้ากันนี้

### ขอบเขต trigger และลำดับผล

- สิทธิ์ “ครั้งแรกต่อรอบ” เป็นของ **ผู้สวมแต่ละคน + power ID + round** ใช้ค่านับรอบจาก resolver ไม่ใช่เวลาแอนิเมชัน รีเซ็ตในการต่อสู้ใหม่ ไม่ใช่ตอนเปิดหน้าต่างหรือรีโหลด
- Aegis: ทำผลโจมตี การลดดาเมจ โล่ และกติกากันตายเดิมก่อน หาก HP ลดจริงและผู้รับยังมี HP > 0 ให้ผลครั้งเดียวหลัง hit และก่อน hit ถัดไปของคำสั่ง ถ้า HP ไม่ลดหรือผู้สวมล้มไม่ใช้สิทธิ์ ป้องกัน reflect/thorns สร้าง trigger วน
- Focus: ตรวจ Mark ก่อนสกิลเดิมลบ Mark; โบนัสไม่ใช้/ยืด Mark เพิ่มเอง รวม +4 เข้า damage event ของเป้าหมายหลักก่อนจำกัดที่ HP คงเหลือและคำนวณดูดเลือด ไม่สร้าง hit แยกและไม่กระตุ้น chain เพิ่ม สกิลเป้าหมายเดี่ยวที่พ่วง splash เพิ่มเฉพาะเป้าหมายหลัก ท่าที่เพียงควบคุมและ power = 0 ไม่เข้าเงื่อนไข
- Lantern: `heal` ต้องเพิ่ม HP ให้เพื่อนคนอื่นจริงก่อน จากนั้นจบ barrier/talent ปกติ แล้วใช้ max กับ 6 ไม่บวกซ้อน ไม่ลด barrier เดิมและไม่ถือว่า barrier นี้เป็น Ward ที่สะท้อนดาเมจ
- ถ้าเงื่อนไขผ่านแต่มีโล่ >= 6 อยู่แล้ว ให้คงโล่เดิมและใช้สิทธิ์รอบนั้นตามคำว่า “ครั้งแรก” ไม่รอใช้สิทธิ์ใหม่หลังโล่แตกในรอบเดียวกัน
- ไม่เกิดผลจากการดู preview; preview และ replay ต้องสร้างผลเดียวกับการ commit สถานะ used ต้องอยู่ใน simulation ไม่ซ่อนใน DOM
- หลายคนใส่ชิ้นชนิดเดียวกันได้ ผลเป็นของตนเอง ไม่มีออร่าสะสม; ต่อคนมีเครื่องประดับได้ชิ้นเดียว

### Affixes และตัวอย่างคุณภาพ 100%

ทุกชิ้นมีสาม affixes ที่ไม่ซ้ำ จาก pool เครื่องประดับเดิม เริ่มต้นสุ่มโดยรับประกัน affix ประจำแนวทางหนึ่งช่อง: Aegis = HP, Focus = Attack, Lantern = Support อีกสองช่องสุ่มจากที่เหลือ การันตีนี้ใช้เฉพาะตอนดรอป หลังจากนั้นสุ่มใหม่/ถ่ายโอนช่องนี้ได้ ไม่ทำให้ item ผิดกติกาและไม่คืน affix เดิมให้อัตโนมัติ

| ตัวอย่างในต้นแบบ Lv11 +0 / q100 | ค่าสถานะหลัก | Affixes ตัวอย่าง |
|---|---|---|
| Aegis | Support +18% | HP +14, Support +10%, Luck +5 |
| Focus | Support +18% | Attack +10%, SPD +3, Leech +8% |
| Lantern | Support +18% | Support +10%, HP +14, Luck +5 |

ค่า Support ในตารางเป็นแยกหลัก/affix; Aegis/Lantern รวม +28% แต่ Focus รวม +18% ตัวอย่างไม่ใช่ blueprint ตายตัวหรือหลักประกันสาม affixes เดียวกันทุกดรอป

## 4. ฟาร์มและกันดวงตก — ค่าร่าง

- คงอุปกรณ์ปกติสามชิ้นและกติกาอาวุธ/เซ็ตเดิม เพิ่มช่องโบนัสเครื่องประดับบอสแยก **ไม่แทนที่อาวุธที่กำลังนับรับประกัน**
- ค่าย → แผนฟาร์ม มีหัวข้อบอสแยก เลือกหนึ่งในสามชิ้นล่วงหน้า เป้าถูก snapshot ตอนออกเดินทาง เหมือนแนวทางเลือกอาวุธ ไม่มีค่าใช้จ่าย ถ้าไม่เลือก ใช้ Aegis เป็นค่าเริ่มต้นและแสดงให้ทราบ
- ชัยชนะบอสครั้งแรกของโปรไฟล์หลังระบบนี้เริ่มใช้ รับประกันชิ้นที่เลือกหนึ่งชิ้น โปรไฟล์เก่าที่เคยจบบทแล้วก็ได้สิทธิ์นี้หนึ่งครั้งเมื่อชนะบอสหลังอัปเดต ไม่แจกย้อนหลังทันทีจากการโหลดเซฟ
- หลังจากนั้น มีโอกาส 25% ต่อชัยชนะบอส; ไม่ดรอปสามชัยชนะติดกัน ครั้งที่สี่รับประกันชิ้นที่เลือก **หนึ่งชิ้นเท่านั้น** ชัยชนะครั้งแรก/สุ่มสำเร็จ/รับประกัน ล้วนรีเซ็ตตัวนับเป็น 0
- ตัวนับเป็นรายบอส ไม่แยกรายชิ้น เปลี่ยนเป้าแล้วคงความคืบหน้า นับชัยชนะบอสที่ resolve จริงเท่านั้น แพ้/หนี/มินิบอส/ร้าน/ตีบวกไม่เพิ่มหรือล้าง
- รีเซ็ตเมื่อเกิดดรอปจริง ไม่รอถึงค่าย แม้ภายหลังเสียของตามกติกา wipe เดิมก็ไม่คืนสิทธิ์ซ้ำ ชัยชนะและ reward ต้อง commit/save ครั้งเดียว ปิดเกมก่อนกดรับผลไม่สุ่มซ้ำ
- โบนัสอยู่ใน found จนกลับค่าย: “พบของ” ยังไม่เท่ากับ “นำกลับแล้ว” ใช้กติกา wipeKeep เดิม ไม่ให้ special retention แฝง; ถ้าคลังเต็มเข้าถาดรอจัดการเดิม ไม่หาย ไม่ auto recycle
- Boss bonus ไม่เดินตัวนับหาอาวุธ ไม่ใช้ Luck เพิ่มโอกาส 25% ไม่เพิ่มโอกาสเซ็ต/คุณภาพ และไม่เกิดจากคลิกปุ่มจำลอง/เปิดข้อมูล
- รอบเดินทางเก่าที่ยังไม่จบต้องใช้เส้นทาง loot/RNG เดิมต่อจนกลับค่าย ไม่แทรก RNG ใหม่เข้ากลางการต่อสู้เก่า เปิดระบบใหม่เฉพาะการออกเดินทางที่มี versioned boss-loot snapshot การจ่ายโบนัสใหม่ใช้ stream/counter ที่แยก domain จากการสุ่มของปกติอย่างชัดเจน

### ตรวจความคาดหวังทางคณิตศาสตร์

หลังรางวัลแรก: ให้ p = 0.25 และบังคับสำเร็จในครั้งที่ 4

| ได้ของในชัยชนะที่ | ความน่าจะเป็น |
|---|---:|
| 1 | 25% |
| 2 | 18.75% |
| 3 | 14.0625% |
| 4 | 42.1875% |

ค่าเฉลี่ย = `1 + 0.75 + 0.75² + 0.75³ = 2.734375` ชัยชนะบอสต่อชิ้น **ไม่ใช่จำนวนครั้งต่อ affixes/quality ที่ต้องการ** การแพ้และเวลาต่อการเดินทางยังไม่รวม จึงต้องวัดเวลาจริงก่อนสรุปว่าฟาร์มสบาย

หลังรางวัลแรก อัตราในระยะยาวประมาณ `1/2.734375 = 0.365714` ชิ้นโบนัสต่อชัยชนะ ต้องประเมินผลเพิ่มทรัพยากรจากรีไซเคิลสีทองด้วย ไม่พิจารณาเฉพาะพลังต่อสู้ ความคืบหน้าที่แสดงต้องเป็น “โอกาส 25% / อีกไม่เกิน N ชัยชนะบอส” ไม่ใช่ “สุ่มครบ 4 ครั้ง” หรือรับประกันระดับคุณภาพสูงสุด

## 6. UX ที่จะใช้ร่วมกัน

- ไม่มีปุ่มถาวรใหม่บนสนาม การพบของเปิดรายละเอียดได้จากผลชัยชนะ/สรุปการเดินทาง; ของที่มีแล้วเปิดจากกระเป๋า/ตัวละครร่วมกันเหมือนเดิม
- รายละเอียดมีแท็บ **รายละเอียด / เปรียบเทียบ / แหล่งดรอป** ไม่ซ้อน native dialog ใน character dialog เดิม ใช้ subview พร้อมกลับตำแหน่ง/โฟกัสเดิม
- ส่วนบน: icon เดิมแบบ vector, ชื่อ, สี, Lv, +, อาชีพที่ใส่ได้, ป้าย “เฉพาะผู้คุมรอยแยก” และล็อก แสดงพลังบอสก่อน affixes
- รายละเอียด: trigger/ปริมาณ/ข้อจำกัด/สถานะรอบนี้เมื่อมีข้อมูลศึกจริง แสดง icon+ข้อความ ไม่พึ่งสีล้วน; แยก “พลังบอส” ออกจาก “คุณสมบัติถ่ายโอน”
- เปรียบเทียบ: ค่าสถานะจริงทั้งตัวก่อน/หลัง + Active เดิม + เซ็ต/special ที่เสีย แยกดาเมจพื้นฐานกับโบนัสเมื่อเงื่อนไขทำงาน; บน MAP ให้ดูเป็นเงื่อนไขสมมติ ไม่อ้างว่าใช้สิทธิ์ในศึกไปแล้ว
- ถ้าอาชีพไม่มีท่าตาม trigger บอกตรง ๆ เช่น “ไม่มี Heal — พลังประทีปไม่ทำงานกับตัวละครนี้” Auto-equipment ต้องไม่ให้คะแนนโบนัสมีเงื่อนไขเป็นดาเมจคงที่หรือเลือกเพราะสีทองอย่างเดียว
- แหล่งดรอป: ชื่อบอส/พื้นที่/เป้าที่ snapshot/25%/ตัวนับ/สิทธิ์ครั้งแรก/ยังต้องนำกลับค่าย ปุ่มเปลี่ยนเป้ากลับไปแผนฟาร์มที่ค่าย และไม่เปลี่ยนเป้าระหว่างรัน
- ปุ่มสวมใส่อยู่ footer ของหน้าตัวละครและใช้ reducer/revalidation เดิม กดดู/สลับแท็บ/ทดลองเงื่อนไขไม่สวม ไม่เปลี่ยน HP ไม่เขียนเซฟ
- กรอบสูงสุด 480px; กรอบจริงใช้ #app + @container game; ปุ่ม/แท็บ >=44px; เนื้อหาเลื่อนในกรอบ footer อยู่ถึงได้ที่ 320×568; Arrow/Home/End สำหรับแท็บ; Esc กลับ; ขณะหมุน/เปิด modal/กดค้าง/พิมพ์ห้ามเกิดคำสั่งซ้ำ
- ต้นแบบ HTML เป็นตัวอย่างโต้ตอบแยกจากเกม ใช้ข้อมูลตัวอย่างที่ระบุชัด ไม่อ้างว่าเชื่อม resolver หรือมีปุ่มสวมใส่จริง

## 7. เกณฑ์ตรวจระบบก่อนเผยแพร่

1. เพิ่ม content catalog ของ unique ID → boss/slot/rarity/power; แยก `Item.boss` จาก `special` ทั่วไป และตรวจ slot/rarity/normal-set/no-generic-special ให้ครบ ห้ามเชื่อข้อความชื่ออุปกรณ์เป็นแหล่งกติกา
2. เพิ่มการตรวจทุกเส้นทาง item: found UID0, owned UID, overflow, equip, forge/ledger, loss/return, active-run provenance; unique ID ที่ไม่รู้จักหรือจับคู่ผิดต้องปฏิเสธ ไม่มีการสร้างพลังบอสให้ของเก่า
3. เพิ่ม metadata target/pity/first-reward รายบอสพร้อม snapshot/migration; ออกแบบ transaction ชัยชนะให้บันทึก reward และ counter พร้อมกัน ไม่แก้ profile แล้วลืม run หรือจ่ายสองครั้งหลัง reload
4. เพิ่ม power ใน pure resolver, state, battle log, snapshot และ preview/replay; render-only badge อ่าน effect ที่เกิดจริง ไม่เปิดเผยผลใน stage อนาคต
5. ตัดสิน encounter version bump สำหรับ rule semantics ใหม่ ตาม CLAUDE.md พร้อมแผนรองรับเซฟค้างศึกเก่า/การกลับค่ายก่อนใช้กติกาใหม่ ห้ามเพิ่ม gear power แล้วเงียบ ๆ ทำให้ active battle เก่า replay ต่างไป
6. รัน simulation เทียบของปกติ/เซ็ต/ทอง special เดิม กับชิ้นบอสที่ Lv,+,quality ใกล้กัน ครบสิบอาชีพ และแยกเทียบตามงบพัฒนา ทดสอบไม่ติดตรา/ติดตรา, shield รับหมด/ทะลุ/ตาย, รักษาเต็ม/บาดเจ็บ, ศัตรูเดี่ยว/หลายตัว และหลายรอบ ห้ามสรุปพลังจากดาเมจ dummy อย่างเดียว
7. เป้าหมายการยอมรับ: ไม่มี infinite loop/immortality; bonus ขึ้นเพดานตามเงื่อนไข; มีตัวเลือกเซ็ต/ทองเดิมที่ยังดีกว่าในบางสถานการณ์; preview=commit=replay; ผลหนึ่ง victory จ่ายของ/นับครั้งเดียว; ตัวนับอาวุธและ ordinary RNG ไม่เปลี่ยนจากช่องโบนัส
8. ตรวจ economy ทั้งการฟาร์มและรีไซเคิล ไม่มีวงจรคืนทุนเกินจริง และวัดเวลาจริงต่อรอบเพื่อทบทวน p25%/hard4 ก่อนประกาศเป็นค่าจริง
9. ค่อยเชื่อม shared UI แล้วตรวจ typecheck/lint/unit/build/Playwright ที่เกี่ยวข้องและ CI เดิมก่อน merge/deploy; Chromium touch emulation ไม่เท่ากับทดสอบ iPhone/Safari จริง

ลำดับพัฒนาที่แนะนำหลังร่างนี้: **catalog/identity/save และ ordinary-loot compatibility → resolver/preview/replay + simulation → reward/pity transaction → shared UI/forge/storage → regression และเผยแพร่** ทั้งชุดต้องเสร็จก่อนถือว่าอุปกรณ์บอสใช้งานได้จริง
