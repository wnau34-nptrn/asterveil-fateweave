**Asterveil · Fateweave — ข้อเสนอระบบออนไลน์และรายได้**

เจ้าของถามต่อถึงทางเลือกกาชาตัวละครเต็มรูปแบบ พร้อมแพ็กพัฒนาและ Season Pass: ดู [ข้อเสนอกาชาเพิ่มเติม](GACHA_MONETIZATION_PROPOSAL_TH.md) ซึ่งเป็นอีกโมเดลธุรกิจและยังไม่เปลี่ยนกฎเกมจริง

วิเคราะห์วันที่ 20 ตุลาคม 2026 (Asia/Bangkok) จากโค้ดและเอกสารใน checkout นี้ และเอกสารทางการที่ระบุเป็นลิงก์ ข้อเสนอทั้งหมดเป็นแนวทางสำหรับงานถัดไป ไม่ได้เปลี่ยนกฎเกมเดิม เพิ่มเซิร์ฟเวอร์ เปิดร้านค้า หรือเปิดรับเงินจริง ตัวเลขราคา ระยะเวลา เป้าหมายทดสอบ และรายได้ด้านล่างเป็นสมมติฐานสำหรับวางแผน ยังไม่มีข้อมูลผู้เล่นจริงหรือผล load test รองรับ

**1. ทิศทางที่แนะนำ**

พัฒนาเป็น Online Tactical Expedition RPG: ผู้เล่นเป็นผู้บัญชาการกองทหารรับจ้าง มีบริษัทและความก้าวหน้าถาวร จัดทีม สำรวจแผนที่แบบช่อง ต่อสู้ด้วย SPD เก็บอุปกรณ์ และกลับมาพัฒนาค่าย เพิ่มเพื่อน กิลด์ ภารกิจชุมชน และการร่วมผจญภัยเป็นห้องตามลำดับ

ลำดับที่เหมาะกับทีมเล็กคือ เกมหลักที่เล่นซ้ำสนุก → บัญชีและเซฟออนไลน์ที่เซิร์ฟเวอร์ควบคุม → กิจกรรมที่เล่นคนละเวลาได้ → Co-op 2 คน → ร้านสินค้าตกแต่ง → ค่ายที่พบผู้เล่นอื่น → พิจารณาโลก MMORPG ที่ใหญ่ขึ้นตามจำนวนผู้เล่นและกำลังดูแลจริง

จุดขายควรเป็นการจัดกองทหารและอ่านลำดับ SPD เพื่อชนะรอยแยก ความรู้สึกเป็นโลกออนไลน์เกิดจากความก้าวหน้าร่วมและชุมชนได้ โดยยังไม่จำเป็นต้องจำลองผู้เล่นหลายร้อยคนบนแผนที่ต่อสู้เดียวกัน

หากทีมยังเล็กและไม่มีงบทำเนื้อหาต่อเนื่อง ทางธุรกิจที่เบากว่าคือทดลองเล่นฟรีแล้วซื้อเกมหลัก/บทเนื้อหา พร้อมแพ็กสนับสนุนและสกิน การทำ F2P เต็มรูปแบบควรเกิดเมื่อมีหลักฐานว่าคนกลับมาเล่นและทีมผลิตเนื้อหาได้สม่ำเสมอ

**4. ประสบการณ์ที่ควรออกแบบให้ครบ**

ช่วงเริ่มต้น: ทดลองเล่นบทนำ → เข้าใจหน้าที่อาชีพและ SPD → เห็นคอมโบที่ตนเลือก → ชนะบอสแรก → ได้อุปกรณ์ที่เปลี่ยนวิธีจัดทีม → กลับค่ายและเข้าใจเป้าหมายถัดไป ให้คนเห็นความสนุกก่อนพบข้อเสนอจ่ายเงิน

วงจรหนึ่งรอบ: เลือกภารกิจ → จัดกองทหาร → เดินสำรวจ/เปิดทาง/แก้ปริศนา → ตัดสินใจเรื่องความเสี่ยงและทรัพยากร → ต่อสู้ → ถอนตัวหรือปราบบอส → จัดของและพัฒนาทีม → ทดลองบิลด์ในรอบต่อไป

เสนอเป้าหมายการเล่นบนมือถือ 10–20 นาทีต่อ expedition สั้น โดยทดสอบจริงก่อนยืนยัน ด่านยาวควรพักและกลับมาเล่นต่อได้จากสถานะบนเซิร์ฟเวอร์ ไม่บังคับลงยาวทุกครั้งเพื่อได้ความก้าวหน้าหลัก

เหตุผลที่กลับมาในสัปดาห์ถัดไปควรมาจากเป้าหมายบิลด์ บอสที่มีวิธีรับมือต่างกัน เรื่องราวใหม่ และคนในกิลด์ ควรมีภารกิจรายสัปดาห์สะสมได้ แทนการทำงานประจำวันหลายรายการที่กดดันให้ล็อกอินทุกวัน

| Endgame | ดันเจียนปรับเงื่อนไข บอสหลายรูปแบบ การล่าเซ็ตเฉพาะพื้นที่ และ challenge ชุดอุปกรณ์มาตรฐาน | เพิ่มเมื่อวงจรพื้นฐานพร้อม |
| เพื่อน | รหัสเชิญ ดูโปรไฟล์ ยืมทีมช่วยแบบจำกัด และรางวัลที่ไม่เปิดช่องปั๊มบัญชี | ออนไลน์ระยะแรก |
| กิลด์ | สมาชิก บทบาท ประกาศ เป้าหมายร่วม และของตกแต่งกิลด์ | เริ่มเรียบง่ายหลังพิสูจน์การกลับมาเล่น |
| Co-op | เชิญเพื่อน ห้องพร้อมเล่น สิทธิ์ควบคุม เทิร์นหมดเวลา ต่อกลับ และของรางวัลรายคน | หลังเซิร์ฟเวอร์น่าเชื่อถือ |
| ร้านค้า | แสดงสินค้าจริง ราคา สิทธิ์ที่ได้รับ ใบเสร็จ สถานะส่งของ และติดต่อช่วยเหลือ | หลังระบบธุรกรรมพร้อม |

อย่าเปิดหลายโหมดที่ต้องจับคู่ตั้งแต่แรก ฐานผู้เล่นน้อยจะกระจายจนหาเพื่อนร่วมทีมยาก ให้เริ่มหนึ่งโหมด Co-op ที่เล่นคนเดียวได้เมื่อไม่มีคนพร้อม

การเพิ่ม “อาชีพใหม่” ควรเพิ่มวิธีเล่น มากกว่ามีค่าสถานะสูงกว่าอาชีพเดิม การเพิ่มระดับไอเทมทุกฤดูกาลจนของเก่าหมดคุณค่าจะเร่งภาระฟาร์มและผลิตเนื้อหา ควรเน้นชุดบิลด์และเงื่อนไขด่านมากขึ้น

**6. วิธีทำ Co-op ให้เข้ากับกฎปัจจุบัน**

แนะนำเริ่ม 2 ผู้เล่น บัญชีละ 2 ตัวลงสนาม รวม 4 ตัวเช่นเดิม ต่อไปจึงเพิ่ม 4 ผู้เล่นคนละ 1 ตัว รูปแบบนี้รักษาจำนวนช่องต่อสู้และความอ่านง่ายบนจอแนวตั้ง การเอาบริษัทเต็ม 4 ตัวของทุกบัญชีมารวมเป็น 16 ตัวจะเปลี่ยนสมดุล ความยาวศึก และ HUD มาก

ในด่าน Co-op แรก กำหนดทีมร่วม 4 ตัว ไม่มีชุดสำรองอิสระ 4 ตัวต่อบัญชีระหว่างด่าน ส่วนการเล่นเดี่ยวคง 4 + 4 ตามเดิม หากเพิ่มสำรองร่วมภายหลังให้กำหนดจำนวนและจุดสลับชัดเจน ห้ามนำกฎสำรองหลายชุดมารวมโดยไม่มีการออกแบบ

| จุดตัดสินใจ | ข้อเสนอเริ่มต้น |
|---|---|
| เดินสำรวจ | หัวหน้าทีมกดเดินทีละช่องด้วยตนเอง สมาชิกเห็นตำแหน่งและหมอกชุดเดียวกัน |
| เริ่มบอส/ถอนตัว | มีการพร้อมเล่นหรือโหวตก่อนขั้นที่กระทบทั้งทีม พร้อมทางออกเมื่อหัวหน้าหลุด |
| การต่อสู้ | SPD จัดลำดับทั้งทีม เจ้าของตัวที่ถึงเทิร์นเท่านั้นออกคำสั่งได้ |
| ระยะคิดต่อเทิร์น | ทดลอง 25–35 วินาทีและระบบเวลาเผื่อ เปลี่ยนได้หลังดูพฤติกรรมจริง |
| หมดเวลา | ตัวจัดการออนไลน์ฝั่งเซิร์ฟเวอร์เลือกคำสั่ง fallback ที่ถูกกฎและบันทึกเหมือนคำสั่งปกติ ไม่ใส่นาฬิกาใน pure resolver |
| เน็ตหลุด | เผื่อกลับเข้าห้องตามนโยบาย เช่น 60–90 วินาที ส่ง snapshot ล่าสุด และจัดการเทิร์นค้างได้ |
| คนออกกลางทาง | เล่นต่อด้วย fallback/AI ที่กำหนดไว้ ไม่ให้คนเดียวจับทั้งห้องค้างไม่จำกัด |
| ของรางวัล | แต่ละบัญชีได้รางวัลส่วนตัวตามเงื่อนไข ไม่มีแย่งกดเก็บ และรับได้ครั้งเดียวต่อผลด่าน |
| ชวนเพื่อนเลเวลต่างกัน | ทำช่วงพลัง/การปรับสเกลที่แสดงชัด ทดลองกับคู่ผู้เล่นใหม่และเก่า |

ข้อเทคนิคเฉพาะเกมนี้: ต้องแยก instance ID ของตัวที่ลงศึกออกจากรหัสต้นแบบอาชีพ เช่น Mira จากสองบัญชีต้องเป็นคนละ actor และมี ownerPlayerId คนละค่า ห้ามใช้ heroId ของต้นแบบเป็นตัวพิสูจน์ความเป็นเจ้าของ จำนวนช่องทีมคงเดิมไม่ได้แปลว่าต่อหลายบัญชีได้โดยไม่แก้แบบจำลองข้อมูล

การข้ามแอนิเมชันทำได้เฉพาะการแสดงผล ไม่ทำให้ผู้เล่นส่งคำสั่งข้ามสิทธิ์หรือเปลี่ยนเวลาที่เซิร์ฟเวอร์ตัดสินผล กฎนี้ต่อยอดจากการแยก simulation กับ presentation ที่มีอยู่แล้ว

**7. เศรษฐกิจและความก้าวหน้าที่ต้องวางก่อนเติมเงิน**

เก็บทอง แร่ ฝุ่น และตราเป็นทรัพยากรที่หาในเกมต่อไป หากมีเงินพรีเมียมให้ใช้กับของตกแต่งเท่านั้น ช่วงแรกขายสกินเป็นราคาเงินบาทตรง ๆ ได้เพื่อลดความซับซ้อนของยอดคงเหลือและเศษเงิน

การขายตราทดแทนตัวซ้ำ การจ้างเพิ่ม ดาว อุปกรณ์แรงกว่า หินตีบวก หรือสิทธิ์ reroll เพิ่ม ย่อมซื้อความก้าวหน้าหรือพลังได้ ถึงร้านจะใช้คำว่า “ความสะดวก” ก็ต้องประเมินผลต่ออันดับ เศรษฐกิจ และเวลาเล่นจริง

| ประเด็น | แนวทาง |
|---|---|
| สิ่งที่สร้างเงิน/ทรัพยากร | ชัยชนะ บอส ภารกิจ หีบ รางวัลกิจกรรม และสิ่งชดเชย ต้องมีบันทึกแหล่งที่มา |
| สิ่งที่ใช้เงินถาวร | การจ้าง ร้านค้า การเลือกเปลี่ยนบิลด์บางส่วน ระบบค่าย/สูตรที่ใช้ทรัพยากรจริง และค่าธรรมเนียมตลาดในอนาคต |
| ต้นทุนตีบวกที่คืนเต็ม | เป็นทุนที่พักไว้ในไอเทม ไม่ใช่ resource sink ถาวร ต้องคำนวณเศรษฐกิจแยก |
| การฟาร์มซ้ำ | วัดผลตอบแทนต่อเวลา จำนวนรอบ และกระเป๋าของบัญชีเก่า/ใหม่ ป้องกันเส้นทางผลิตทรัพยากรไม่จำกัดจาก bug |
| การเปลี่ยนบิลด์ | รักษาจุดแข็งเรื่องคืนต้นทุนและ reset ที่เป็นธรรม ไม่สร้างค่าใช้จ่ายใหม่เพียงเพื่อบังคับซื้อ |
| การล่าของ | ระบุพื้นที่ที่มีโอกาสพบเซ็ต และมีวัตถุดิบ/แต้มแลกช่วยให้ค่อย ๆ เข้าใกล้เป้าหมาย |
| คลังและของล้น | รักษาการไม่ทำลายของเงียบ ๆ และช่องทางขยายด้วยเงินเกม กำหนดเพดานเชิงบริการด้วยนโยบายที่แจ้งล่วงหน้าเมื่อจำเป็น |
| ฤดูกาล | เก็บของซื้อและความก้าวหน้าหลัก รีเซ็ตเฉพาะอันดับ/challenge ที่แจ้งไว้ หรือเปิดตัวละครฤดูกาลแบบสมัครใจ |

ต้นทุนที่คืนเต็มต้องคืนครั้งเดียวพร้อมบริโภค/ทำลายไอเทมในธุรกรรมเดียว ป้องกันการกดพร้อมกันข้ามอุปกรณ์แล้วได้ทั้งของและทรัพยากรคืน หากเพิ่มซื้อขาย ต้องกำหนดว่าประวัติทุนติดตามไอเทมหรือผู้จ่ายอย่างไรและทดสอบวงจรทำกำไรซ้ำ

ไม่แนะนำขาย EXP boost, drop boost, energy ฟาร์มเพิ่ม หรือสิทธิ์ reset บอสที่ให้ของเพิ่มในช่วงที่ยังต้องพิสูจน์ความเป็นธรรม ถ้าเลือกโมเดลขายความก้าวหน้าจริงต้องสื่อสารอย่างตรงไปตรงมาและออกแบบโหมดแข่งขันใหม่รองรับ

**8. ระบบ MMO ระยะยาวที่ควรรู้ภาระก่อนเพิ่ม**

ค่ายส่วนกลาง: เริ่มเป็นรายชื่อผู้เล่น/โปรไฟล์/ห้องชวนทีมก่อน การเดินเห็น avatar คนอื่นเพิ่มภาระ sync และตรวจสถานะ เสนอเพดานออกแบบเบื้องต้น 20–40 คนต่อห้องค่ายเพื่อใช้ทดสอบ ไม่ใช่ผลยืนยันความสามารถของเซิร์ฟเวอร์

บอสโลก: เริ่มจากแต่ละบริษัทสู้ใน instance แล้วเซิร์ฟเวอร์รวมผลงานเป็นความคืบหน้าชุมชน มีรางวัลส่วนร่วมที่ไม่ให้คนตีสุดท้ายได้ทั้งหมด โหมดนี้ไม่ต้องให้ทุกคนต่อสู้พร้อมกันในสนามเดียว

กิลด์: เริ่มเป้าหมายร่วมและของตกแต่ง ให้รางวัลช่วยเหลือผู้เล่นใหม่ด้วย แต่ตรวจปั๊มบัญชี ไม่เพิ่มสงครามยึดพื้นที่ก่อนมีกิลด์และจำนวนผู้เล่นที่ทำให้กิจกรรมเกิดจริง

PvP: เริ่มแบบสมัครใจหรือ challenge ชุดตัวละคร/อุปกรณ์มาตรฐาน แยกรางวัลความสามารถออกจากพลังสะสม หากทำ ranked ภายหลังต้องมีการจับคู่ ข้อจำกัดเวลา การกลับเข้าห้อง การตรวจสมยอม และสมดุลเฉพาะโหมด

SPD เป็นค่าสำคัญมากเพราะเปลี่ยนลำดับการลงมือ ต้องทดสอบว่ามีชุดความเร็วที่บังคับเมตาหรือไม่และคอมโบ stun/delay วนได้หรือไม่ ก่อนเพิ่มการแข่งขัน ความสามารถแบบ deterministic ยังต้องทดสอบการค้นหาคำตอบและบอต ไม่ถือว่ามี replay แล้วอันดับจะเป็นธรรมโดยอัตโนมัติ

ตลาดผู้เล่น: เลื่อนไปหลังเศรษฐกิจนิ่ง หากเปิด ให้ใช้เงินที่หาในเกม รายการสินค้าที่อนุญาต ค่าธรรมเนียม การผูกของหลังสวม และบันทึกเจ้าของ ห้ามเริ่มพร้อมการถอนเป็นเงินจริง เพราะเพิ่มปัญหามูลค่าทางการเงิน การฉ้อโกง และการปฏิบัติตามกฎหมายอย่างมาก

ที่อยู่อาศัย/ตกแต่งค่าย: เหมาะกับการแสดงตัวตนและขายของตกแต่ง แต่ควรเริ่มเป็นพื้นที่เล็กและของประกอบที่มีต้นทุนผลิตคุมได้ ระบบก่อสร้างโลกเต็มรูปแบบเป็นอีกงานใหญ่

แอปที่เผยแพร่ผ่าน Google Play ต้องใช้ Play billing สำหรับสินค้า/บริการดิจิทัลในแอป เว้นแต่เข้าเงื่อนไขข้อยกเว้น ส่วน Apple มีข้อกำหนด IAP และข้อยกเว้นตาม storefront/entitlement จึงไม่ควรสมมติว่าสามารถย้ายปุ่มเติมเงินจากเว็บไปใส่แอปได้เหมือนกันทุกประเทศ [Google Play Payments](https://support.google.com/googleplay/android-developer/answer/9858738?hl=en), [Apple Payments](https://developer.apple.com/app-store/review/guidelines/#payments)

Steam ระบุให้การซื้อในเกมของลูกค้า Steam ผ่าน Steam Wallet และ microtransaction API ต้องคำนวณรายรับสุทธิและสิทธิ์ข้ามแพลตฟอร์มจากสัญญา/เงื่อนไขจริงก่อนเปิดช่องทางนั้น [Steamworks Microtransactions](https://partner.steamgames.com/doc/features/microtransactions)

GitHub Pages ปัจจุบันเป็นฐานเผยแพร่ต้นแบบ เอกสาร GitHub ไม่อนุญาตใช้เป็น free hosting เพื่อดำเนินธุรกิจออนไลน์/e-commerce หรือบริการเชิงพาณิชย์ตามที่ระบุ ก่อนทำเกมบริการแบบมีร้านและบัญชีจริง ควรย้ายส่วนบริการไป hosting/CDN ที่อนุญาตการใช้งานนั้น และแยก backend อย่างชัดเจน รายงานนี้ไม่ได้ย้ายหรือเปลี่ยนการเผยแพร่ [GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)

**11. ระบบซื้อขายที่ต้องทำให้ถูกตั้งแต่รายการแรก**

ผู้เล่นเลือกสินค้า → เซิร์ฟเวอร์สร้างออร์เดอร์จากราคาใน catalog → ผู้ให้บริการรับชำระเงิน → เซิร์ฟเวอร์ตรวจผลจาก webhook/API ที่เชื่อถือได้ → บันทึกสิทธิ์/รายการบัญชีและสถานะส่งมอบในธุรกรรมเดียว → ผู้เล่นรับของพร้อมประวัติใบเสร็จ

ห้ามให้หน้า “ชำระสำเร็จ” ใน browser หรือภาพสลิปเป็นตัวสั่งเพิ่มของโดยตรง ต้องมีหมายเลขออร์เดอร์ ผู้ซื้อ สินค้า ราคา สกุลเงิน ช่องทาง และหมายเลขธุรกรรมผู้ให้บริการที่ผูกกันได้

| เหตุการณ์ | พฤติกรรมที่ต้องได้ |
|---|---|
| ชำระสำเร็จ แต่ผู้เล่นปิดหน้าไปแล้ว | ส่งสิทธิ์เข้าบัญชีได้ และเห็นเมื่อกลับมา |
| webhook ส่งซ้ำ หรือคนกดตรวจสถานะซ้ำ | ให้ของเพียงครั้งเดียวต่อการซื้อ แม้มีหลาย event |
| event มาผิดลำดับ | ตรวจสถานะปัจจุบันกับข้อมูลผู้ให้บริการ ไม่ย้อนออร์เดอร์ผิด |
| รับ event แล้วบริการล่ม | เก็บงานไว้ให้ retry และกู้การส่งมอบได้ |
| QR หมดอายุ/จ่ายไม่ครบ/ราคาเปลี่ยน | ใช้เงื่อนไขออร์เดอร์ที่ตกลงไว้และมีทางช่วยเหลือ |
| คืนเงิน/ถูกยกเลิกธุรกรรม | บันทึกปรับสิทธิ์ตามนโยบาย มีหลักฐานและช่องทางอุทธรณ์ |
| ซื้อสกินเดิมซ้ำจากอีกเครื่อง | ตรวจสิทธิ์ก่อนและหลังชำระ กำหนดคืนเงินหรือชดเชยอย่างชัดเจน |

ควรมีตาราง order, provider transaction, processed event, fulfillment, entitlement, refund และ ledger ที่ตรวจย้อนหลังได้ พร้อม unique constraints ระดับการซื้อ ไม่ใช้เพียง flag ในหน่วยความจำของเซิร์ฟเวอร์ Stripe ระบุว่า webhook อาจซ้ำและไม่ได้รับประกันลำดับ event [Stripe Webhooks](https://docs.stripe.com/webhooks)

สำหรับสินค้าแรกที่เป็นสกินตรง ๆ ยังไม่ต้องสร้าง wallet เติมเพชร หากมี wallet ภายหลังให้แยกยอดซื้อ/ยอดแจกและประวัติ debit/credit พร้อมกฎคืนเงินที่ตรวจสอบได้ ไม่เชื่อยอดที่ client ส่งมา

**12. สถาปัตยกรรมที่เสนอ**

| ส่วน | ข้อเสนอเริ่มต้น | ขอบเขตความรับผิดชอบ |
|---|---|---|
| Client | Phaser + TypeScript เดิม และ DOM UI | แสดงภาพ เก็บ input แสดงสถานะชั่วคราว |
| Game API | Node.js + TypeScript, เริ่มเป็น backend หนึ่งชุดแบ่ง module | ตรวจสิทธิ์ คำสั่ง เดินโลก ต่อสู้ รางวัล และการพัฒนา |
| กฎร่วม | ยก pure core เดิมเป็น package/module ที่ server ใช้จริง | ผลเกมอ้างอิงกฎชุดเดียวกับการทดสอบ |
| ฐานข้อมูล | PostgreSQL | โปรไฟล์ ไอเทม เจ้าของ สถานะด่าน ธุรกรรม สิทธิ์ซื้อ และ log สำคัญ |
| Authentication | บริการ managed เช่น Supabase Auth | สมัคร/ล็อกอิน ผูกบัญชี และ recovery โดยไม่สร้างระบบรหัสผ่านเอง |
| สื่อสาร | HTTPS สำหรับคำสั่ง/บัญชี เพิ่ม WebSocket เมื่อมีห้องและสถานะร่วม | reconnect, resync, presence และอัปเดต Co-op |
| Room service | เพิ่ม Colyseus เมื่อความต้องการห้องร่วมชัดเจน | จัดห้องและกระจาย state ไม่แทนฐานข้อมูลธุรกรรม |
| Background worker | งานจากฐานข้อมูล/queue ตามขนาดงาน | ส่งของซื้อ ประมวลผลกิจกรรม จัดอันดับ และ retry |
| CDN/Storage | ไฟล์ build รูป เสียง และ log archive ตามนโยบาย | ลดภาระส่ง asset จาก game server |
| Monitoring/Admin | metrics, error log, audit, เครื่องมือช่วยเหลือ | ตรวจปัญหาและดำเนินการกับข้อมูลอย่างมีหลักฐาน |

Supabase Auth รองรับหลายวิธีล็อกอินและเชื่อม JWT/RLS ส่วน Colyseus มี authoritative rooms และการ sync state ทั้งสองเป็นตัวเลือกตามความต้องการ ไม่จำเป็นต้องเพิ่มทุกผลิตภัณฑ์ก่อนมีเหตุผล [Supabase Auth](https://supabase.com/docs/guides/auth), [Colyseus](https://docs.colyseus.io/)

ถ้าใช้ฐานข้อมูลที่ expose API ต้องตั้งสิทธิ์และ RLS ให้ถูก ผู้เล่นอ่านข้อมูลที่ตนมีสิทธิ์เห็นได้ แต่การเพิ่มทอง ผลบอส ตีของ และให้สิทธิ์ซื้อ ต้องผ่าน game service ที่ตรวจคำสั่ง ห้ามให้ browser เขียนค่าสำคัญตามใจหรือฝัง service secret ไว้ใน build [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)

คำสั่งออนไลน์ควรมีตัวตนที่ตรวจแล้ว, request ID, version ของสถานะ, run/battle ID และข้อมูลคำสั่ง ตัว server ตรวจสิทธิ์ตัวละครและ beat อีกครั้ง จากนั้น commit ทั้งผลและรางวัลแบบ atomic แล้วค่อยกระจายการแสดงผล ธุรกรรมช่วยให้การเปลี่ยนหลายตารางเกิดครบหรือไม่เกิดเลย แต่ยังต้องออกแบบ locking/version/unique constraints รองรับคำสั่งชนกัน [PostgreSQL Transactions](https://www.postgresql.org/docs/current/tutorial-transactions.html)

เริ่มจาก modular monolith และฐานข้อมูลหนึ่งชุดก่อน เพิ่มหลาย process, Redis หรือแยกบริการเมื่อมีผลวัดว่าต้องใช้ อย่าใช้ฐานข้อมูลเป็น message bus กระจายทุกเฟรม หรือวาง Kubernetes หลายบริการก่อนพิสูจน์เกม Turn-based ไม่จำเป็นต้องส่ง combat state 60 ครั้งต่อวินาที

**13. ย้ายจากเกมในเครื่องเป็นบริการออนไลน์อย่างไร**

1. สร้างบัญชีออนไลน์และ environment ทดสอบแยกจาก production
2. เริ่มเศรษฐกิจออนไลน์จากข้อมูลที่เซิร์ฟเวอร์สร้าง เซฟเดิมเก็บไว้เล่นเดี่ยว/แสดงความสำเร็จแบบไม่เข้าอันดับได้ แต่ไม่แปลงทรัพยากรที่แก้ได้เป็นทุนซื้อขายออนไลน์โดยอัตโนมัติ
3. เปลี่ยนการเดิน ต่อสู้ จ้าง อัปเกรด โรงตีเหล็ก รับรางวัล และย้ายไอเทมให้เป็นคำสั่งที่ server ประมวลผลเอง
4. เก็บ RNG หรือ seed ที่มีผลต่อรางวัลบน server และไม่ส่งข้อมูลอนาคตให้ client เดาจุดดรอป ค่า seed/rolls ที่เปิดให้เครื่องกำหนดในเกมเดิมต้องทบทวนก่อนใช้กับบริการจริง
5. ใช้รหัสไอเทมที่ไม่ชนข้ามบัญชี ผูกเจ้าของและ revision กับทุกการย้าย item ห้ามเชื่อค่า investment ที่ client อ้าง
6. อนุญาตหลายอุปกรณ์อ่านสถานะ แต่ serialize/reject คำสั่งแก้สถานะที่ชนกัน ไม่ทำ last-write-wins กับเงินและกระเป๋า
7. ทำ migration ที่สำรองและกู้คืนได้ ข้อมูลที่อ่านไม่ผ่านต้องเก็บหลักฐานและให้ซ่อมได้ ไม่ใช้การล้างโปรไฟล์และซื้อใหม่เป็นทางออก
8. กำหนด wipe policy ของ closed beta ให้ชัดก่อนเปิดทดสอบ และยังไม่รับเงินจริงจนทดสอบ restore/fulfillment/refund ผ่าน

การตรวจ replay ช่วยตรวจความถูกต้องตามกฎ แต่ไม่พิสูจน์ว่าผู้เล่นได้ seed, ของตั้งต้น, เงิน และสิทธิ์นั้นมาโดยชอบ เซิร์ฟเวอร์ต้องเป็นผู้เริ่ม run กำหนดการสุ่ม และอนุมัติรางวัล ไม่รับแค่ log ที่ผู้เล่นเลือกส่งหลังรู้ผลแล้ว

ถ้าจะคงการเล่น offline ให้แยกความก้าวหน้าที่เครื่องควบคุมออกจากเศรษฐกิจออนไลน์ หากต้องการนำเข้าความสำเร็จใด ต้องกำหนดรางวัลแบบจำกัดที่ไม่เปิดช่องย้ายของ/เงินซ้ำ

**14. สิ่งที่ทีมต้องดูแลหลังเปิดบริการ**

| งาน | ขอบเขตขั้นต่ำ |
|---|---|
| เสถียรภาพ | health checks, error alerts, latency, backup และการซ้อม restore |
| เครื่องมือ GM | ดูเหตุการณ์บัญชี ค้นออร์เดอร์ ตรวจของ แก้ปัญหาด้วยเหตุผลและ audit log จำกัดสิทธิ์ผู้ดูแล |
| ความปลอดภัย | TLS, secret management, rate limit, ตรวจสิทธิ์, MFA สำหรับ admin, ป้องกัน bot/abuse ตามข้อมูลที่พบ |
| ชุมชน | รายงานผู้เล่น บล็อก แบน/อุทธรณ์ ป้องกัน spam และดูแล chat หากเปิด |
| อัปเดตเกม | staging, version compatibility, rollback, maintenance mode และปิด feature บางส่วนได้ |
| Live operations | ตารางกิจกรรม รางวัลชดเชยที่รับครั้งเดียว และตรวจผลต่อเศรษฐกิจ |
| การเงิน | กระทบยอดรายวัน/รายเดือน เงินเข้าธนาคาร ค่าธรรมเนียม คืนเงิน และสิทธิ์ที่ค้างส่ง |
| การบริการลูกค้า | ช่องทางติดต่อ SLA ภายในทีม กระบวนการกู้บัญชีและปัญหา “จ่ายแล้วไม่ได้ของ” |

แผนเนื้อหาเริ่มต้นที่คุมงานได้: หมุน challenge จากชุดเงื่อนไขที่ทดสอบแล้วในแต่ละสัปดาห์ มีกิจกรรมกิลด์ที่สะสมได้ และอัปเดตใหญ่เมื่อของพร้อม แทนการสัญญาอาชีพหรือแผนที่ใหม่ทุกเดือนก่อนรู้ต้นทุนจริง

ก่อนรับเงินให้มีเงื่อนไขบริการ นโยบายคืนเงินและสิทธิ์ของสินค้า แนวปฏิบัติข้อมูลส่วนบุคคล/การลบบัญชี การดูแลผู้เล่นอายุน้อย และตรวจสิทธิ์ภาพ เพลง ฟอนต์ให้ครบ แยกข้อมูลที่ลบได้จากบันทึกธุรกรรมที่ต้องเก็บตามกฎหมาย โดยให้ผู้รับผิดชอบตรวจตามตลาดที่จะเปิดจริง

ต้องตรวจภาษีและรูปแบบผู้ประกอบการ รายได้จาก e-commerce มีหน้าที่ทางภาษีตามเงื่อนไขกฎหมายเช่นเดียวกับกิจการทั่วไป ให้ทำบัญชีและกำหนดราคาหลังดูภาษี/สัญญาของแต่ละช่องทาง ไม่ถือยอดขายรวมเป็นเงินที่นำไปใช้ได้ทั้งหมด [กรมสรรพากร: ภาษีที่เกี่ยวข้อง](https://www.rd.go.th/26218.html) ส่วนแนวทางข้อมูลส่วนบุคคลให้ตรวจจาก [สำนักงานคณะกรรมการคุ้มครองข้อมูลส่วนบุคคล](https://gppc.pdpc.or.th/)

**15. คิดรายได้ให้สัมพันธ์กับต้นทุน**

รายได้จากร้านต่อเดือนโดยประมาณ = ผู้เล่นที่กลับมาเล่นในเดือนนั้น (MAU) × สัดส่วนคนจ่ายในเดือนนั้น × ยอดจ่ายเฉลี่ยต่อคนจ่ายในเดือนนั้น (ARPPU)

| กรณีสมมติ | MAU | คนจ่าย | ARPPU/เดือน | ยอดขายรวม/เดือน |
|---|---:|---:|---:|---:|
| ฐานเริ่มต้น | 1,000 | 3% = 30 คน | 300 บาท | 9,000 บาท |
| ชุมชนขนาดเล็กที่กลับมาเล่น | 10,000 | 3% = 300 คน | 300 บาท | 90,000 บาท |
| เติบโตและขายของได้ดีขึ้น | 30,000 | 4% = 1,200 คน | 300 บาท | 360,000 บาท |

ตัวเลขเหล่านี้ไม่ได้ทำนายว่าจะมีผู้เล่นหรือคนจ่ายเท่าใด ยอดดาวน์โหลดและบัญชีสมัครสะสมใช้แทน MAU ไม่ได้ และยอดขายข้างบนยังไม่หักค่าช่องทาง ภาษี คืนเงิน การตลาด ค่าแรง งานศิลป์ หรือระบบบริการ

ตัวอย่างจุดคุ้มรายจ่ายประจำ: สมมติต้องรองรับค่าใช้จ่าย 50,000 บาท/เดือน และสมมติเหลือ 85% ของยอดขายหลังรายการหักแบบแปรผัน คนหนึ่งจ่าย 300 บาท จะเหลือ 255 บาท ต้องมีคนจ่ายอย่างน้อย 197 คน/เดือน หรือประมาณ 6,600 MAU เมื่อคนจ่ายคิดเป็น 3% ตัว 15% ที่หักเป็นสมมติฐาน ไม่ใช่ค่าธรรมเนียมจริงของร้านหรือ gateway ใด และยังต้องกันภาษี/ต้นทุนที่ไม่ได้อยู่ใน 50,000 บาทแยกต่างหาก

| ถ้าสมมติเหลือจากยอดขาย | เงินเหลือต่อผู้จ่าย 300 บาท | ผู้จ่ายขั้นต่ำเพื่อรองรับ 50,000 บาท |
|---|---:|---:|
| 95% | 285 บาท | 176 คน |
| 85% | 255 บาท | 197 คน |
| 70% | 210 บาท | 239 คน |

ค่าพัฒนาที่จ่ายไปก่อนเปิดเกมต้องมีแผนคืนทุนอีกส่วน จุดคุ้มรายจ่ายรายเดือนยังไม่ใช่การคืนทุนโครงการทั้งหมด และการรับเงินแพ็กรายปี/ขายเครดิตล่วงหน้าสร้างภาระส่งมอบในอนาคต ไม่ควรใช้ยอดเงินเข้าเพียงอย่างเดียวสรุปกำไร

ต้องทำงบอย่างน้อย: ค่าแรงตัวเอง/ทีม, ศิลป์/เสียง/แปล, production+staging+backup+log, authentication/email, bandwidth/storage, payment/refund, บัญชี/กฎหมาย, community/support, การหาผู้เล่น และเงินสำรองช่วงรายได้ลด

ยังไม่ควรเสนอราคาเซิร์ฟเวอร์รายเดือนตายตัวจากจำนวนบัญชี ต้องมี workload ที่ระบุ command ต่อวินาที, peak CCU, room size, ระยะเวลาเก็บ log, ขนาดข้อมูล/asset และความพร้อมใช้งาน แล้ว load test และขอราคาจริงอย่างน้อยสองทางเลือก

ด้านการหาผู้เล่น เริ่มจาก demo ที่ส่งลิงก์ให้เพื่อนได้ วิดีโอสั้นโชว์การพลิกเกมด้วย SPD หน้าเกมที่บอกความสนุกชัด ชุมชนทดสอบ และแนะนำเพื่อนที่ไม่ให้รางวัลพลังจนปั๊มบัญชีคุ้ม ซื้อโฆษณาแบบขยายวงเมื่อรู้ต้นทุนต่อผู้เล่นที่กลับมาเล่นและมูลค่าระยะยาวแล้ว

ตัวชี้วัดที่ควรติดตาม: จบบทนำ/บอสแรก, D1/D7/D30 retention แยก cohort, expedition จบ/ถอน/แพ้, เวลาในเทิร์น, ความหลากหลายบิลด์, ทรัพยากรสร้าง/ใช้, อัตราชวนเพื่อน, เวลารอ Co-op, คนจ่าย/ซื้อซ้ำ, กำไรส่วนเพิ่มต่อ cohort, ปัญหาซื้อของ และต้นทุน support ต่อผู้เล่น

**16. ลำดับการพัฒนาและกำลังทีม**

สมมติทีมหลัก 2–4 คนที่ทำ client/server ได้ มีงาน art/QA ตามช่วง เวลาด้านล่างเป็นกรอบวางงานเบื้องต้นหลังตรวจรายละเอียด ไม่ใช่วันส่งมอบหรือคำรับรอง และไม่ใช่ประมาณการ MMORPG เต็มรูปแบบ

| ระยะ | ผลส่งมอบ | กรอบเวลาสมมติ | เงื่อนไขไปต่อ |
|---|---|---|---|
| A. เกมหลักและเก็บข้อมูล | บทนำสนุก expedition เล่นซ้ำได้ จบได้บนเครื่องจริง telemetry ที่จำเป็น | 4–8 สัปดาห์ | คนเข้าใจและอยากเริ่มรอบใหม่ ปัญหาจอ/ประสิทธิภาพหลักถูกแก้ |
| B. Online authority | บัญชี server-side profile/run/commands, economy, backup และ migration | 6–10 สัปดาห์ | แก้ client แล้วเพิ่มเงิน/ของไม่ได้ หลายเครื่องไม่ทำของซ้ำ และ restore ผ่าน |
| C. เล่นคนละเวลา | โปรไฟล์เพื่อน challenge บอสชุมชน/กิลด์อย่างใดอย่างหนึ่ง | 4–6 สัปดาห์ | มีการกลับมาและใช้ปฏิสัมพันธ์ โดย support รับไหว |
| D. Co-op 2 คน | ห้อง ชวนเพื่อน สิทธิ์ควบคุม timeout/reconnect และ reward ต่อบัญชี | 6–10 สัปดาห์ | คู่ผู้เล่นใหม่เล่นจบได้ เน็ตหลุดไม่ค้าง และไม่แจกของซ้ำ |
| E. Paid beta | สินค้าขายตรงเล็กน้อย checkout/order/fulfillment/refund/admin และ production hosting | 4–6 สัปดาห์ | ทดสอบการเงินและกู้ระบบผ่าน พร้อมคนรับผิดชอบหลังเปิด |
| F. ขยายชุมชน | ค่ายร่วม Co-op 4 คน กิลด์ลึกขึ้น endgame และ pass เมื่อพร้อม | ใช้ข้อมูลจริงกำหนด | ผู้เล่นและรายรับรองรับต้นทุนเพิ่ม |

กรอบ A–E รวมแบบเรียงกันประมาณ 24–40 สัปดาห์ก่อนเวลาเผื่อ integration/rework งานบางส่วนทำร่วมกันได้ แต่มี dependency ต่อกัน ควรเผื่อประมาณ 25–40% ตามความไม่แน่นอน ทีมคนเดียวที่ทำ art, support และการเงินด้วยควรลด scope และไม่ใช้ตารางของทีมหลายคนเป็นกำหนดส่งของตน

สำหรับทีมคนเดียว/งบต่ำ: จบเกมหลัก → cloud save/authority → asynchronous หนึ่งระบบ → ขายเกม/แพ็กตกแต่งที่ส่งมอบได้ เลื่อน shared hub, Co-op 4 คน, chat เปิด, ตลาดผู้เล่น และ PvP ranked

สำหรับทีมที่มีงบและคนดูแล: ใช้แผน A–E แล้วกำหนดเจ้าของงานชัดเจนด้าน client/gameplay, backend/economy, art/content, QA/live operations หากไม่มีคนรับผิดชอบการเงินและปัญหาบัญชี ยังไม่ควรเปิดเงินจริงถึงแม้ checkout จะทำงานแล้ว

**17. เกณฑ์ทดสอบก่อนเปิดรับเงินจริง**

1. เซิร์ฟเวอร์ปฏิเสธการปลอมเงิน ของ seed รางวัล และคำสั่งตัวละครของคนอื่น
2. ส่งคำสั่งเดิมซ้ำ/หลายแท็บ/สองอุปกรณ์ ไม่มีการใช้ของหรือรับรางวัลเกินครั้งที่ถูกต้อง
3. หลุดเครือข่ายหลัง commit แต่ก่อนรับ response แล้วกลับมาเห็นผลเดิม ไม่ยิงซ้ำและไม่เสียของ
4. ต่อกลับ Co-op, คนออกกลางเทิร์น และหัวหน้าหลุด ไม่ทำให้สมาชิกที่เหลือเล่นต่อไม่ได้
5. ชำระสำเร็จ/ล้มเหลว/ค้าง/ซ้ำ/ผิดลำดับ/คืนเงิน และล่มระหว่างส่งมอบ มีผลถูกต้อง ตรวจย้อนหลังและกระทบยอดได้
6. migrate และ restore จาก backup ใน environment ทดสอบผ่าน โดยรักษาของและสิทธิ์ที่ซื้อ
7. load test ด้วย command mix จริงทั้งช่วงเปิดตัวและกิจกรรม กำหนดเพดานที่ระบบรับได้และการลดภาระเมื่อเกิน
8. เล่นจริงบน Android และ iPhone/Safari รวมล็อกจอ เปลี่ยนแอป สัญญาณสลับ และเครือข่ายช้า การจำลอง touch บน Chromium อย่างเดียวไม่พอ
9. มี dashboard/alert และคนรับปัญหาบัญชีหรือจ่ายแล้วไม่ได้ของ พร้อมเครื่องมือซ่อมที่มี audit
10. สินค้า ราคา เงื่อนไข สิทธิ์ข้ามอุปกรณ์ ข้อมูลส่วนบุคคล และข้อกำหนดช่องทางขายถูกตรวจแล้วสำหรับประเทศที่เปิด

เริ่ม paid beta ด้วยสินค้าขายตรงที่ไม่ถ่ายโอนและไม่มีโบนัสพลัง ช่วยลดพื้นที่ข้อผิดพลาด ก่อนเพิ่มยอดเงินพรีเมียม ของขวัญ การแลกเปลี่ยน และสมาชิกต่ออายุ

**18. ขอบเขตงานถัดไปที่เหมาะสม**

ทำเอกสารออกแบบ Online MVP หนึ่งชุดและ prototype แนวตั้งหนึ่งเส้น: ล็อกอิน → รับบริษัทใหม่จาก server → เข้าด่านเดี่ยว → ส่งคำสั่งสู้ → รับรางวัลครั้งเดียว → เปิดจากอีกเครื่องเห็นสถานะเดียวกัน → ซ้อม restore ได้ เส้นนี้พิสูจน์ปัญหาหนักของออนไลน์ก่อนเพิ่มระบบสังคมหลายชุด

เมื่อเส้นนี้ผ่าน จึงทำ Co-op ทดลอง 2 คนหนึ่งด่าน พร้อมข้อมูลวัดว่าคนสนุกกับการรอและแบ่งตัวละครหรือไม่ คำตอบนี้จะช่วยเลือกระหว่าง co-op พร้อมกันกับออนไลน์ที่เล่นคนละเวลา และเป็นหลักฐานก่อนลงทุนกับค่ายร่วม/โลก MMORPG เต็มรูปแบบ
