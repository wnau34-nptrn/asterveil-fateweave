# แผนงานเอฟเฟกต์การต่อสู้และคัตซีนบอส

วันที่ 21 ตุลาคม 2026 · สถานะ: เฟส 0–1 เสร็จ; เฟส 2 พัฒนา C20–C25 แล้ว กำลังตรวจและเผยแพร่; เฟส 3–5 ยังไม่เริ่ม

ผลเฟส 0: [สเปกและ storyboard](combat-presentation/PHASE0_SPEC_TH.md), [ตารางครอบคลุม](combat-presentation/COVERAGE_TH.md), [asset brief](combat-presentation/ASSET_BRIEF_TH.md), [baseline 21/21 flows](combat-presentation/BASELINE_TH.md) ผลเฟส 1 C10–C16: [พฤติกรรมและหลักฐานตรวจ](validation/COMBAT_PRESENTATION_PHASE1.md) ไม่เปลี่ยนกฎต่อสู้/เซฟ/ดรอป; สถานะ deployment ดูผลตรวจนั้น

อ้างอิง [ข้อเสนอการนำเสนอการต่อสู้](COMBAT_PRESENTATION_PROPOSAL_TH.md), `CLAUDE.md`, `UI_DESIGN.md` และโครงสร้างเกมปัจจุบัน แผนนี้แปลงข้อเสนอเป็นงานที่ลงมือและตรวจรับได้ ดูสถานะที่ทำเสร็จจาก checkbox และหลักฐานแต่ละเฟส ไม่ถือว่างานที่เหลือเสร็จจากการมีสเปกแล้ว

## 1. เป้าหมายและขอบเขตส่งมอบ

ผู้เล่นต้องเห็นการโจมตีเดินทางถึงเป้า รู้สึกถึงน้ำหนักจากภาพและเสียงที่ตรงกัน แยกหน้าที่ของสกิลได้ และรู้สึกว่าบอสเป็นเหตุการณ์สำคัญ โดยการเล่นซ้ำเพื่อฟาร์มยังคล่องตัว

**ชุดเผยแพร่แรก:** ระบบจังหวะร่วม, เอฟเฟกต์พื้นฐาน, สกิลหลักของทีมเริ่มต้นสี่อาชีพ, ผู้คุมรอยแยกครบ intro/สองท่าหลัก/defeat, การข้าม/ฉากย่อ/ลด motion และการทดสอบก่อนเผยแพร่ ทุกอาชีพและทุกแอ็กชันต้องมี fallback ที่ถูกต้อง แม้เอฟเฟกต์เฉพาะยังอยู่ชุดถัดไป

**ชุดขยาย:** เอฟเฟกต์เฉพาะอาชีพที่เหลือและสกิลปลดดาว, มินิบอส, พลังอุปกรณ์/เซ็ตที่ระบุแหล่งได้จริง และเพิ่มคุณภาพเสียง/ภาพต่อจากชุดแรก

**ไม่รวม:** เปลี่ยน damage/HP/SPD/cooldown, เพิ่มคริติคอล, เพิ่มบอสหรือเฟสที่มีกฎใหม่, เปลี่ยนดรอป/พิตี้/เศรษฐกิจ, สร้างวิดีโอยาวหรือเสียงพากย์ และวาดแอนิเมชันเต็มทุกเฟรมให้ตัวละครทุกตัว

## 2. ลำดับและจุดตรวจรับ

| เฟส | งานหลัก | สิ่งส่งมอบ | ต้องเสร็จก่อน | ขนาดงานสัมพัทธ์ |
|---|---|---|---|---|
| 0 — เตรียมสเปกและหลักฐาน | บันทึกฉบับเดิม, ทำรายการสกิล/ผลรอง, กำหนด cue และ asset brief | สเปกเวลาและรายการงานที่ตรวจสอบได้ | ไม่มี | เล็ก–กลาง |
| 1 — ระบบกำกับจังหวะ | ตัวเล่น cue ที่ยกเลิกได้, snapshot ที่ถูกต้อง, คิวเสียง/ตัวเลข, fallback | เล่นผลเดิมด้วยภาพใหม่โดยไม่เปลี่ยนผลต่อสู้ | เฟส 0 | ใหญ่ |
| 2 — การต่อสู้พื้นฐาน | เส้นฟัน/กระสุน/impact, ป้องกัน/รักษา, ทีมเริ่มต้นสี่อาชีพ | ต้นแบบคุณภาพจริงที่เล่นได้ครบไฟต์ | เฟส 1 | กลาง |
| 3 — ผู้คุมรอยแยก | Intro, Crushing Blow, Rift Bolt, defeat, ฉากย่อ/ข้าม | บอสตัวอย่างครบวงจร | เฟส 1–2 และ asset บอส | กลาง–ใหญ่ |
| 4 — ตรวจชุดแรกและเผยแพร่ | correctness, input, viewport, performance, audio, CI/Pages/live | ชุดเผยแพร่แรกและหลักฐานตรวจรับ | เฟส 1–3 | กลาง ขึ้นกับปัญหาที่พบ |
| 5 — ขยายเนื้อหา | ทุกอาชีพ/สกิลดาว, มินิบอส, อุปกรณ์และเซ็ต | ชุดขยายที่ผ่านเกณฑ์เดียวกับชุดแรก | ระบบจากเฟส 1–4 | ใหญ่ ขึ้นกับ asset |

เส้นทางหลัก: **0 → 1 → 2 → 3 → 4 → 5** เตรียมภาพ/เสียงของเฟส 3 ได้หลัง brief เฟส 0 คงที่ ระหว่างพัฒนาระบบฐานได้ งานนี้ไม่กำหนดให้ใช้ subagents

ขนาดงานเป็นการประเมินความซับซ้อน ไม่ใช่จำนวนวันหรือกำหนดส่ง หลังเฟส 0–1 จึงประเมินระยะเวลาที่เหลือจากต้นแบบและเวลาผลิต asset จริง ไม่รวมเวลารอผู้ทดสอบ/อุปกรณ์/บริการภายนอกเป็นเวลาพัฒนาที่แน่นอน

## 3. งานที่ต้องดำเนินการรายเฟส

### เฟส 0 — เตรียมก่อนแตะระบบ

- [x] **C00 — เก็บ baseline:** บันทึกวิดีโอหรือเฟรมต่อเนื่องของโจมตีธรรมดา, Mark→Execute, Bolt, Guard, Ward/Heal, การสวนและการชนะบอส พร้อมข้อมูล command/state ที่ทำซ้ำได้ เก็บหลักฐานทดสอบนอก repo ตามวิธีเดิม ไม่แก้เซฟจริงของผู้ใช้
- [x] **C01 — ทำตารางครอบคลุม:** ทุก action, enemy intent และ event type มีหมวด physical/magic/support, ต้นทาง/เป้าหมาย, เวลา, เสียง, ผลรอง, fallback และสถานะ asset ตรวจชื่ออาชีพ/สกิลจาก content จริง
- [x] **C02 — ล็อกภาษาเอฟเฟกต์:** ฟ้า–ทองฝ่ายทีม/ม่วงรอยแยกฝ่ายศัตรู, รูปทรงตามอาวุธ/หน้าที่, น้ำหนัก light/heavy/support, ระดับแรงภาพ และกติกาตัวเลขไม่ทับ status
- [x] **C03 — วาง storyboard:** ผู้คุมรอยแยก 3.2s, รอบฟาร์ม 0.6–0.9s, ปิดฉาก 1.4–2s; เขียนข้อความสั้นให้ตรง lore และยืนยันว่าใช้ Sentinel ปัจจุบัน ไม่แทนเป็นวาร์กอธ
- [x] **C04 — ทำ asset manifest/brief:** รายการด้านล่างพร้อมผู้รับผิดชอบงานโค้ด/ภาพ/เสียง/QA, ที่มาและสิทธิ์, ขนาด, จุด anchor, ระยะเวลา, ชื่อ key และ fallback ไม่เริ่มผลิต asset ทั้งเกมก่อนเห็นต้นแบบ

**ผ่านเฟสเมื่อ:** มีตัวอย่างฉบับเดิมที่ทำซ้ำได้ ทุก action มี fallback และสเปกเวลารวมทั้งงานภาพ/เสียงพร้อมนำไปสร้างต้นแบบได้

### เฟส 1 — ระบบกำกับจังหวะและความถูกต้อง

- [x] **C10 — Presentation contract:** กำหนดลำดับ `prepare → travel → impact → reactions → recover` และข้อมูลก่อน/หลัง stage ให้ชัด ใช้ข้อมูลจาก resolver เป็นจริง ไม่คำนวณกฎ damage/โล่/ดูดเลือดซ้ำใน UI
- [x] **C11 — ตัดสินใจเรื่องผลรอง:** ตรวจว่าข้อมูล `TurnStage`/events เพียงพอสำหรับจังหวะย่อยหรือไม่ กรณี reflection/leech/barrier/down ทำให้ต้องเห็นค่าหลายช่วง ให้สร้าง trace/snapshot สำหรับการนำเสนอ ณ จุดที่ resolver เปลี่ยนค่าจริง โดยคงผลลัพธ์เดิม ห้ามย้อนคำนวณจากข้อความ log หากข้อมูลยังไม่พอ ให้เปิดเผยผลทั้งกลุ่มตรง impact เดียวอย่างซื่อตรงจนมี trace ที่ตรวจได้
- [x] **C12 — ตัวเล่นที่ยกเลิกได้:** cue ทุกตัวมีเจ้าของ session/stage และช่องทาง cancel เดียว รวม timer, tween, delayed SFX และการ duck เพลง ป้องกัน callback เก่ามาทำงานในไฟต์ใหม่
- [x] **C13 — แยก render ข้อมูลกับเริ่ม animation:** ป้องกัน `render()/scene.sync()/paint()` จากการล้าง VFX ทั้งชุดทุกครั้งที่ HP หรือข้อความเปลี่ยน ออกแบบ update เฉพาะ projection หรือ rebuild ที่กู้ตำแหน่ง cue ได้ ตรวจ resize ไม่ทำให้เหตุการณ์เล่นซ้ำ
- [x] **C14 — จัดคิวผล:** HP/barrier/status/log/ตัวเลข/เสียงอ่าน projection เดียวกัน ไม่เผยผลของ actor ถัดไป; ความยาว stage อิง cue สุดท้ายและเวลาอ่านผล แทนการรอ 1,000ms ทุกท่า
- [x] **C15 — lifecycle และ input:** skip/ซ่อนแท็บ/เปลี่ยนศึก/rotation/resize ต้องมีพฤติกรรมกำหนดไว้และจบที่ state เดียว ยกเลิก effect/เสียงค้าง คืนตำแหน่งและ focus และไม่ส่งคำสั่งของฮีโร่คนถัดไปจากปุ่มที่กดค้าง
- [x] **C16 — compatibility:** ตรวจ replay/preview, เซฟ active battle เดิม และ shape ที่ validator ตรวจ คาดว่าไม่ต้องเปลี่ยน save v27 ถ้า trace เป็นข้อมูลชั่วคราวที่สร้างใหม่ได้ แต่ให้ตรวจจริงก่อนตัดสินใจ ไม่เพิ่ม version เพียงเพื่อ effect

**ผ่านเฟสเมื่อ:** ผลการต่อสู้เท่ากับ baseline, ผลรองแสดงลำดับถูก, ข้ามทุกช่วงแล้วไม่เกิด damage/รางวัลซ้ำ และไม่มี timer/เสียงหลุดไปยัง stage หรือไฟต์ถัดไป

### เฟส 2 — เอฟเฟกต์พื้นฐานและทีมเริ่มต้น

- [x] **C20 — ชุดกายภาพ:** เตรียมท่า, เส้นฟัน/แทงเชื่อมเป้า, flash/recoil, hit-stop และสั่นเฉพาะชั้นสนามที่คืนศูนย์ ไม่ย้าย HUD หรือ hit targets
- [x] **C21 — ชุดเวท:** จุดรวมพลัง, projectile ไปถึงตัวเป้า, impact และหางแสง แยกโดนร่าง/โดนโล่/หลบ
- [x] **C22 — ชุด support:** Guard รับแทน, Ward/โล่รับแรง/โล่หมด, Heal/Prayer, Mark, interrupt, cancel และ down ต้องตรงผลจริง รวมฮีลเต็ม HP และไม่มีความเสียหาย
- [x] **C23 — ทีมเริ่มต้น:** ทำ Knight, Duelist, Mage และ Priest ตามสกิลจริง ให้ combo Mark→Execute อ่านออก และการป้องกัน/ขัดจังหวะดูมีคุณค่าเท่าการโจมตี
- [x] **C24 — เสียงและตัวเลข:** ให้ prepare/travel/impact ใช้ cue ร่วมกัน จำกัดเสียงซ้อน จัดช่องตัวเลขเมื่อมีผลต่อเนื่อง และไม่แสดง CRITICAL จากการเลือกชื่อเสียง `crit`
- [x] **C25 — รูปแบบการเล่น:** ตั้งค่าความเร็วปกติ/เร็ว, แรงเอฟเฟกต์มาตรฐาน/ลด และเคารพ reduced-motion; ใช้ fallback ที่ยังเห็นผลสำคัญแม้ปิด motion ค่าตั้งต้นด้านเวลาต้องทดลองก่อนล็อก

**ผ่านเฟสเมื่อ:** เล่นศึกจริงครบไฟต์ได้, เห็นต้นทางถึงเป้า, HP/เสียง/impact ตรงกัน, support อ่านง่าย และแอ็กชันของทุกอาชีพที่ยังไม่มีภาพเฉพาะเล่นผ่าน fallback ได้ครบ

### เฟส 3 — บอสตัวอย่าง

- [ ] **C30 — Intro:** ต่อจาก transition เดิมให้เป็นรอยแยก→เงาร่าง→ภาพใกล้และชื่อ→ลงน้ำหนัก→สนาม ไม่เล่น veil-shatter เดิมและ intro ใหม่ซ้ำยืดเวลาโดยไม่ตั้งใจ
- [ ] **C31 — เริ่มศึกอย่างปลอดภัย:** บันทึก encounter ตามระบบเดิม ฉากเปิดไม่คำนวณผลต่อสู้หรือออกคำสั่งเอง จัดลำดับก่อน `beginBattle`/opening enemy turns ให้ชัด ข้ามแล้วไม่ทำให้ศัตรูเร็วหายไปหรือโจมตีซ้ำ
- [ ] **C32 — Signature:** Crushing Blow เน้นแรงหิน/ทอง; Rift Bolt เน้นการรวมพลัง/วิถีม่วง แสดง cancellation/Guard/barrier ตามผลจริง ไม่สร้างภาพ AoE ให้ท่า single-target
- [ ] **C33 — Defeat/reward:** ใช้ down/outcome จริงทำเกราะแตกและสลาย แสดงดรอปที่คำนวณแล้วเท่านั้น มีทางผ่านทันทีเมื่อ asset โหลดไม่ได้หรือผู้เล่นข้าม ตรวจ boss pity/3 ordinary + bonus ตามระบบเดิม
- [ ] **C34 — การดูซ้ำ:** ค่าเริ่มต้นฉากเต็มเมื่อพบครั้งแรก ฉากย่อในการฟาร์ม ตั้งค่า “ครั้งแรก/ทุกครั้ง/แบบย่อ” แยก preference จาก progression กำหนดการนับว่าเคยดูเมื่อจบหรือกดข้าม และการกลับเข้าหลัง reload ให้แน่นอน
- [ ] **C35 — Fallback และ UI:** ปุ่มข้าม ≥44px อยู่ในกรอบแนวตั้ง, แตะข้ามไม่หลุดสู่สนาม, ไม่มี asset/เสียงก็เข้าเล่นได้, โหลดเฉพาะเมื่อจำเป็นและ preload ก่อนใช้ตามเส้นทางที่เหมาะสม

**ผ่านเฟสเมื่อ:** ฉากเปิด/ท่าหลัก/พ่ายแพ้ต่อกันครบ, รอบฟาร์มกระชับ, skip/reload ไม่เปลี่ยน opening turns หรือรางวัล และไม่เพิ่มกฎบอสใหม่

### เฟส 4 — ตรวจรับและเผยแพร่ชุดแรก

- [ ] **C40 — Automated regression:** ทดสอบ contract/trace/cancellation ด้วยกรณีที่เปลี่ยนผลจริง แล้วรัน typecheck, lint, unit tests และ Pages build ตามมาตรฐาน repo
- [ ] **C41 — Browser regression:** ตรวจขั้นตอนกดสกิล/เลือกเป้า/ข้าม, modal/status, held input, tab hidden, rotation และ resize บนขนาดด้านล่าง แล้วรัน browser suite ตาม workflow เดิม
- [ ] **C42 — ตรวจภาพต่อเนื่อง:** บันทึกวิดีโอหรือเฟรมพร้อม cue timestamp เพื่อเทียบเสียง/flash/recoil/HP/ตัวเลข ไม่ใช้ screenshot เดียวรับรองการ sync
- [ ] **C43 — อุปกรณ์จริง:** วัด frame time และฟัง SFX จริงบนมือถือ Android และ iPhone/Safari; ทดลอง background/resume/mute/unmute และ intro โหลดครั้งแรก หากยังไม่มีเครื่องให้ระบุรายการที่ยังไม่ยืนยัน ไม่อ้างว่า desktop emulation แทนผลนี้ได้
- [ ] **C44 — ประเมินความรู้สึก:** เปรียบเทียบฉบับเดิม/ใหม่ทั้งครั้งแรกและรอบฟาร์ม เก็บคะแนนน้ำหนัก ความเข้าใจ และความรำคาญจากการรอ พร้อมเวลาต่อไฟต์ แล้วปรับตัวเลขเวลา/ความแรงที่ยังเป็นร่าง
- [ ] **C45 — Publish:** ทำ diff review, commit เฉพาะงานนี้, PR/required CI/merge สู่ branch พัฒนาเดิม, Pages deploy, ตรวจเกมสาธารณะและบันทึก handoff ไม่รวมเอกสาร MMO/gacha ที่ค้างอยู่เข้ามาโดยพลการ

**ผ่านเฟสเมื่อ:** ไม่มีความคลาดเคลื่อนของกติกา/เซฟ/input ที่ยังไม่แก้, checks ที่กำหนดผ่าน, หลักฐานภาพ/เสียง/อุปกรณ์ระบุขอบเขตชัด และผล live ตรงกับ build ที่เผยแพร่

## 4. สิ่งที่ต้องเตรียมด้านภาพและเสียง

รายการนี้คือ brief ที่ต้องผลิต/เลือกใช้ในอนาคต ยังไม่มี asset ใหม่ถูกสร้างในงานวางแผนนี้

| หมวด | สิ่งที่ต้องเตรียม | ใช้ใน | แนวทางเริ่มต้น |
|---|---|---|---|
| เส้นโจมตี | โค้งฟัน, แทง, วิถีลูกศร | 2/5 | ใช้รูปทรงใน Phaser ทำต้นแบบก่อน เปลี่ยนเป็น texture เฉพาะเมื่อช่วยคุณภาพ |
| Impact | physical spark, เวทระเบิดเฉพาะจุด, shockwave | 2/3 | โปร่งใส ขอบอ่านชัดบนฉากสว่าง/มืด |
| Support | โล่หกเหลี่ยม/รอยแตกโล่, heal motes, Mark/interrupt | 2 | แยกรูปทรงและไอคอน ไม่ใช้สีอย่างเดียว |
| บอส | ภาพ Sentinel ระยะใกล้, ชั้นเงา/แสงเกราะ, ฉากรอยแยก | 3 | ใช้ดีไซน์เดิมและเตรียมพื้นที่ชื่อ/ปุ่มข้าม; ทดสอบขนาดก่อนเลือกความละเอียดส่งออก |
| พื้น/บอสพ่าย | ฝุ่นหิน, เศษเกราะ, พลังสลาย | 3 | ตกแต่งตามผลจริง ไม่บดบังเป้าหมายหรือใช้เป็นกฎใหม่ |
| UI ชั่วคราว | ชื่อบอส, คัตอินสั้น, ตัวเลือกความเร็ว/แรง/ฉากบอส | 2/3 | ข้อความและปุ่มเป็น DOM; layout ใช้ container `game` |
| SFX พื้นฐาน | whoosh, slash, thrust, magic travel/impact, shield, heal, cancel, down | 2 | แยก onset ชัด ไม่ใส่ความเงียบยาวต้นไฟล์ ปรับความดังให้สม่ำเสมอ |
| SFX บอส | rift open, stone/metal step, heavy slam, rift charge/impact, collapse | 3 | ใช้เพลงบอสที่มีอยู่ ไม่ต้องแต่งเพลงใหม่ในชุดแรก |
| เอกสาร asset | ที่มา/สิทธิ์, key, anchor, frame dimensions ถ้ามี, duration, fallback | ทุกเฟส | เก็บแหล่งที่มาตรวจได้ ไม่ดึงภาพ/โค้ดจาก Rise Beyond |

ภาพเคลื่อนไหวใช้ WebP/PNG หรือ atlas ตาม pipeline เดิมที่ทดสอบได้ ชื่อไฟล์ผูกผ่าน manifest ไม่ฝัง path กระจัดกระจายใน scene เสียงใช้รูปแบบที่พิสูจน์การเล่นบนเบราว์เซอร์เป้าหมายและโหลดเมื่อใช้ กำหนด budget ไฟล์/จำนวน particle หลังวัดต้นแบบ ไม่เพิ่ม dependency หรือ video pipeline โดยไม่มีเหตุจำเป็น

ใช้ภาพปัจจุบันและ synth ทำต้นแบบเวลาได้ก่อน การผลิตภาพบอสละเอียดและเสียงจริงต้องเสร็จก่อนตรวจรับคุณภาพชุดแรก หากยังใช้ placeholder ต้องระบุเป็นรุ่นต้นแบบให้ชัด

## 6. ตารางทดสอบและหลักฐาน

| กลุ่ม | กรณีบังคับ | สิ่งที่ต้องพิสูจน์ |

| Timeline | ก่อน travel/ก่อน impact/หลัง impact/ระหว่างผลรอง/ตอน recover | ข้ามหรือยกเลิกทุกช่วงไม่ทำงานซ้ำ ไม่เหลือเสียงหรือล็อกคำสั่ง |
| ข้อมูลที่เห็น | HP/barrier/status/log/queue และ `!` status inspector | อ่าน snapshot เดียวกัน ไม่เห็นผลอนาคตและไม่คำนวณกฎซ้ำ |
| เซฟ/รางวัล | โหลด active battle เดิม, reload intro/กลางท่า/defeat/reward, บอส guarantee/pity | ไม่มีคำสั่งหรือของซ้ำ/หาย; คงดรอปปกติและโบนัสตามเดิม |
| Input | คลิก/สัมผัส/1–4/Enter/Esc, กดค้าง, typing/IME, modal, rotation | หนึ่งคำสั่งจริงต่อการยืนยันที่ถูกต้อง ข้ามแล้วไม่หลุดเข้าเป้า |
| Viewport | 320×568, 390×844 touch emulation และ 1366×768 desktop; resize ขณะเล่น; touch landscape gate | กรอบแนวตั้งไม่ล้น ปุ่ม ≥44px, HUD/status ไม่ทับร่าง และ canvas/DOM targets ตรง |
| Accessibility | reduced-motion, ลดแรงภาพ, ปิดเสียง, ข้อความยาว | อ่านผล/รู้เป้าหมายได้แม้ไม่มี shake/flash/เสียง |
| ประสิทธิภาพ/เสียง | มือถือจริง, เอฟเฟกต์หนักสุด, โหลดครั้งแรก, background/resume และ iPhone/Safari | วัด frame time/การตอบสนองและฟังจริง; เป้า 60fps เป็นเป้าที่ต้องวัด ไม่ใช่ผลรับรองล่วงหน้า |
| ความรู้สึก | ฉบับเดิมเทียบใหม่, ครั้งแรกเทียบฟาร์มซ้ำ | ผู้เล่นรับรู้แรง/ท่า/ผลได้ดีขึ้น โดยการรอไม่เป็นภาระ |

เริ่มเพิ่ม meaningful tests จาก `tests/battle.test.ts`, `battle-status.test.ts`, `sfx.test.ts`, `tests/browser/combat.spec.ts`, `status.spec.ts`, `portrait-keyboard.spec.ts` และ `world.spec.ts` ตามจุดที่เปลี่ยน เพิ่ม test module เฉพาะ contract เมื่อจำเป็น ไม่เขียน assertion ลอกค่าเวลาใน implementation อย่างเดียว

คำสั่งตรวจตามโครงการ: `npm run typecheck`, `npm run lint`, `npm test`, `npm run build:pages`, `npm run test:browser` และ required CI/workflow เดิม ปรับ focused tests ให้ตรงความเสี่ยงก่อน full regression การจัดทำแผนครั้งนี้ไม่จำเป็นต้องรัน gameplay suite เพราะยังไม่มี runtime เปลี่ยน

## 7. ความเสี่ยงและแนวทางจัดการ

| ความเสี่ยง | วิธีจัดการ |
|---|---|
| ข้อมูล event ไม่พอสำหรับผลต่อเนื่อง | ทำ C10–C11 ก่อน VFX; ใช้ trace จากจุดเปลี่ยนค่าจริงหรือ reveal เป็นกลุ่ม ไม่เดากฎใน UI |
| render ใหม่ล้าง animation กลาง cue | แยก projection update ออกจากเริ่ม playback ตาม C13 พร้อม test resize/status update |
| ฉากซ้ำทำให้ฟาร์มช้า | ฉากย่อเป็นค่าเริ่มต้นหลังดูแล้ว, ข้ามได้, จำกัดคัตอิน และวัดเวลาต่อไฟต์ |
| asset หนัก/โหลดช้า | สร้างต้นแบบด้วยของเดิม/รูปทรงก่อน, โหลดตามการใช้งาน, fallback เข้าเกมได้ |
| เสียงเก่าหลุดข้าม stage หรือ volume เปลี่ยนถาวร | cue cancellation รวมเสียงทุกชั้นและ duck restore; เคารพ mute/volume ผู้เล่น |
| ภาพชี้ว่ามีกฎที่ไม่มีจริง | ผูกเอฟเฟกต์กับ event/target/provenance; ไม่มี CRITICAL/คลั่ง/AoE/ดรอปที่แต่งขึ้น |
| ไม่มีอุปกรณ์จริงสำหรับยืนยัน | แยกผล emulation กับ device จริง; ระบุรายการค้างและไม่รับรองว่า iPhone SFX หายแล้ว |
| งานเอกสารอื่นปน commit | stage เป็นรายไฟล์/hunk และตรวจ diff; รักษา Online/MMO/gacha และ handoff ส่วนเดิม |
