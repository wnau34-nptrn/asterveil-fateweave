## โครงสร้างและงบพื้นที่

หน่วยทั้งหมดคือ CSS px ที่ text scale ปกติ, portrait width 390, safe-area เริ่มต้น 0; พิกัดนับจากมุมบนซ้ายของกรอบเกม ไม่รวมชื่อบอร์ด/คำอธิบายนอกกรอบ

ลำดับ: header คงที่ → body เลื่อนเฉพาะส่วน → dock คงที่ใน flex layout ไม่วางทับเนื้อหา ไม่มี nested scroll ในรายละเอียด ผลหลักไม่ต้องเปิด tab เพิ่ม

| พื้นที่ | x / กว้าง | 390×844: y / สูง | 390×650: y / สูง |
| --- | --- | --- | --- |
| Header | 0 / 390 | 0 / 60 | 0 / 60 |
| Scroll body | 0 / 390 | 60 / 616 | 60 / 422 |
| Dock | 0 / 390 | 676 / 168 | 482 / 168 |
| Identity card — ready | 16 / 358 | 72 / 158 | 72 / 158 |
| Tile อุปกรณ์ | 29 / 96 | 103 / 96 | 103 / 96 |
| แผงขั้นตีบวก | 16 / 358 | 242 / 88 | 242 / 88 |
| แผงผล — neutral | 16 / 358 | 342 / 110 | 342 / 110 |
| รายละเอียด — ขอบนอก | 16 / 358 | 464 / 46 | 464 / 46; ต่อใน body ที่เลื่อนได้ |
| งานอื่นของช่าง | 16 / 358 | 522 / 44 | content y522; เลื่อนขึ้นเพื่อเข้าถึง |
| ช่องวัสดุ | 16 และ 199 / ช่องละ 175 | 689 / 64 | 495 / 64 |
| CTA ready | 16 / 358 | 785 / 48 | 591 / 48 |

เนื้อหา ready แบบย่อมีความสูงรวมประมาณ 518px รวม padding ใน body จึงมีพื้นที่ว่างท้าย body ของจอสูง และต้องเลื่อนประมาณ 96px บนจอเตี้ย ไม่ยืดแผงผลหรือเติมการตกแต่งเพื่อกลบช่องว่าง พิกัดหลังเลื่อนต้องหัก scrollTop ออกจากค่า content

สูตร: `bodyHeight = frameHeight − (60 + safeTop) − (168 + safeBottom)`; ความสูง baseline ไม่ใช่การบังคับตัดข้อความ การขยายชื่อ/รายละเอียด/แถวค่าสถานะต้องทำให้ content สูงขึ้นและเลื่อนต่อได้

## Variants และข้อความยาว

- **Neutral:** ไม่มี header “ก่อน/หลัง/ต่าง” เมื่อไม่มีแถวเปลี่ยน แสดงคำอธิบายตรงจาก preview ปัจจุบัน
- **มีค่าเปลี่ยน:** จัดชื่อค่า → ก่อน → หลัง → delta เป็นข้อมูล DOM ที่อ่านตามลำดับ; ตัวอย่าง `000 → 000 +00` ในบอร์ดเป็น placeholder ชัดเจน ไม่ใช่ stat fixture การเพิ่มแถวทำให้ card โต ไม่พับผลหลัก
- **ไม่มีผู้สวม:** หัวข้อเป็นผลต่ออุปกรณ์ ไม่ใช้ชื่อเอกิสเป็น fallback; เลือกดูผลฮีโร่ได้เฉพาะเมื่อมีข้อมูลจริง
- **ชื่อยาว:** ตัวอย่างทดลองในบอร์ดสูง182px แทน158px โดย tile ยัง96px ปุ่มยัง44px และ dock อยู่ที่เดิม ชื่อทดลองไม่ใช่อุปกรณ์ใหม่ของเกม
- **หลายวัสดุ/ชื่อหรือเหตุผลยาว:** 168px เป็นงบ baseline ของสองวัสดุ ถ้าข้อมูลจริงทำให้เกิน ให้ dock ใช้ intrinsic height, ช่องวัสดุ auto rows และ actions min-height48 แล้วลด body ตามพื้นที่จริง ห้ามใช้ fixed-height พร้อม overflow:hidden
- **Text scaling:** ต้องทำ layout เพิ่มใน prototype ที่ text scale200%; แบบนี้ยังไม่ได้ยืนยันการอ่านครบที่200% ขนาด12ใช้เฉพาะคำอธิบายรอง ไม่ใช้จำนวนที่ต้องตัดสินใจ

## Safe-area และกรอบบน desktop

กรอบตัวอย่าง safe-area แยกกำหนด top24/bottom34 เพื่อทดสอบพื้นที่เท่านั้น ไม่ใช่ตัวแทน iPhone รุ่นใด ต้องนำค่าจริงจากระบบ viewport เดิมมาใช้โดยไม่หัก safe-area ซ้ำ

| Frame | Header | Body | Dock |
| --- | --- | --- | --- |
| 390×844, safe24/34 | 84 | 558 | 202 |
| 390×650, safe24/34 | 84 | 364 | 202 |

สถานะมีค่าเปลี่ยนในบอร์ดแสดงเส้น safe บน/ล่างเพื่ออธิบายระยะ; เส้นและข้อความ safe ไม่อยู่ในเกมที่นำเข้า ใช้กรอบ portrait ของเกมบน desktop ไม่ขยายแผงให้เต็ม monitor ขนาดอื่นนอก390และ safeจำลองสองแบบยังไม่ถือว่าตรวจแล้ว ต้องตรวจ320×568/480px/desktop กับ viewport เดิมก่อนนำเข้า

## การเปิดแบบและตรวจที่ทำแล้ว

ให้บริการโฟลเดอร์ `incoming/ART-UI-UX-002/layout-02` ผ่าน HTTP เช่น `python3 -m http.server 5182 --bind 127.0.0.1 --directory incoming/ART-UI-UX-002/layout-02` แล้วเปิด `http://127.0.0.1:5182` บอร์ดวางสองกรอบเคียงกัน จอแคบจะเรียงต่อกัน แต่แต่ละกรอบคง390pxเพื่ออ่านขนาดจริง

ใช้ Chromium ของ environment ผ่าน Playwright โปรเจกต์กับฟอนต์ self-hosted รอ fonts.ready ก่อนถ่าย DPR1, reduced-motion; Browser JS connector ไม่พร้อมในเซสชันนี้ การเปิด file URL ถูก browser policy บล็อก จึงตรวจผ่าน localhost แทน ไม่เปลี่ยน browser policy

- ตรวจ 14 กรอบ: ขนาด header+body+dock รวมเท่าความสูงกรอบ, ภาพ96px, พื้นที่แตะทุกปุ่ม/summary≥44px, ไม่มี content ล้นแนวนอน
- ตรวจจอ650ทั้ง7 variant ว่าเลื่อนถึง “งานอื่นของช่าง” เหนือ dock ได้ และเปิดรายละเอียดได้
- ไม่มี pageerror/console error ในรอบตรวจสุดท้าย; เก็บ measurements.json หลังแก้พื้นที่แตะ summary ที่พบระหว่างร่างแล้ว
- เปิดดูภาพ ready สองความสูง; เป็น visual/layout check ของแบบ ไม่ใช่ gameplay regression, mobile Safari หรือเครื่องจริง
- ตรวจ whitespace เฉพาะไฟล์ที่เขียนใหม่; OFL สองไฟล์เก็บ trailing whitespace/newline ต้นฉบับไว้เพื่อรักษาสำเนา byte-identical ไม่ปรับข้อความ license
- ภาพ atlas/ฟอนต์คัดลอกแบบ byte-identical จาก source `07f95a7`; ไม่ crop/repaint ภาพหรือออกแบบตัวละครใหม่ มี OFL และ SHA-256 ต้นทางแนบไว้

ยังไม่ได้ตรวจ color contrast ทุกคู่, screen reader, text200%, motion, การคืน focus/ต้นทาง, stale/double-submit หรือ transaction ในแบบนี้ ปุ่มหลักยังไม่มี handler และไม่มี localStorage/API จึงไม่นับว่า flow เหล่านี้ทดสอบผ่าน

## ส่งต่อขั้นที่ 3

ทำ material/token sheet ให้ส่วน header / identity / step / impact / disclosure / resource / CTA ใช้พื้นผิวและเส้นขอบร่วมกัน เทียบ [Artwork01](01_development_concepts.png) โดยรักษาขนาดในเอกสารนี้เป็น baseline พัฒนาวัสดุกรอบจาก CSS ก่อน แล้วค่อยระบุ asset มุม/เส้นประดับที่ต้องวาดในขั้น4

เพิ่มแบบ normal/pressed/focus/disabled และ delta/neutral/insufficient บน component เดียวกัน ห้ามเพิ่มกรอบหนาหรือ ornament ที่ทำให้พื้นที่แตะหรือข้อความถูกบัง ยังไม่ทำ clickable transaction prototype ขั้น5หรือแก้เกมจนถึงงานตามลำดับ

ภาษาภาพนี้ส่งต่อหน้าดาว/สกิล/เพิ่มLvและงานอุปกรณ์อื่นได้ ส่วนผลก่อน–หลังและ review ต้องออกแบบรายคำสั่งตามสเปกเดิม ไม่ถือว่าบอร์ดตีบวกนี้แทน layout ทุกหน้าแล้ว
