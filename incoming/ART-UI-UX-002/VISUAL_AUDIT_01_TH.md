# ขั้นที่ 1 — ตรวจความต่างหน้าตีบวกจริงกับ Artwork

วันที่ 2 พฤศจิกายน 2026 · สถานะ: วิเคราะห์และส่งต่อการออกแบบ ยังไม่ปรับเกม

ต่อยอดแล้วใน [ขั้นที่ 2 Layout พร้อมขนาด](LAYOUT_02_TH.md) ข้อความด้านล่างเป็นผลตรวจ ณ ขั้นที่ 1

## ผลที่ต้องแก้ก่อน

หน้าตีบวกนำร่องมีลำดับงานและปุ่มตรวจรายการแล้ว แต่ภาพรวมยังใกล้หน้าต่างข้อมูลมากกว่าหน้าอัปเกรดแฟนตาซีใน Artwork ความต่างหลักอยู่ที่สัดส่วนภาพอุปกรณ์ ลำดับความเด่นของขั้นตีบวก และวัสดุของแผง ไม่จำเป็นต้องเปลี่ยนระบบเกมเพื่อให้ภาพดีขึ้น

เริ่มจากจัดองค์ประกอบก่อน แล้วจึงเพิ่มแสง/กรอบ การเพิ่มเส้นทองให้ทุกกล่องทันทีจะทำให้หน้าจอรกและยังไม่แก้ลำดับสายตา

## แยกสิ่งที่ต้องเลียนแบบกับข้อมูลตัวอย่าง

ต้องนำทิศทางสีกรมท่า–ทอง–cyan–mint, ผิวแผงมีมิติ, ภาพอุปกรณ์เด่น, ขั้นก่อน→หลัง และปุ่มหลักที่อ่านง่ายมาออกแบบต่อ แต่ดาบ ชื่อตัวละคร ค่าสถานะ จำนวนแถว และต้นทุนใน Artwork เป็นตัวอย่าง ภาพอุปกรณ์ต้องใช้ registry ปัจจุบัน ไม่เปลี่ยนอุปกรณ์/ตัวละครให้ตรงภาพที่ AI วาด

ฉากวิหารนอกโทรศัพท์ หัวชื่อบอร์ด และเส้นประดับรอบงานนำเสนอไม่ใช่องค์ประกอบที่ต้องใส่ลงเกมทั้งหมด ภาพบอร์ดมีหลายหน้าจอและไม่ได้กำหนดขนาด CSS จึงยังไม่อ้าง pixel-perfect หรือเปอร์เซ็นต์ความเหมือนจากภาพนี้

## ผลตรวจจอเตี้ยและข้อจำกัด

ที่ 390×844 item card เริ่ม y70 และ CTA อยู่ x15/y781 ขนาด 360×48 ที่ 390×650 CTA อยู่ y587 และขนาดเดิม ข้อมูล DOM ระบุ body width 390 ทั้งสองขนาด ไม่มี overflow แนวนอนระดับ body ใน fixture นี้ และไม่มี pageerror ระหว่าง capture

ภาพจอเตี้ยแสดง disclosure บางส่วนต่อไปในพื้นที่เลื่อน ขณะที่ค่าใช้จ่าย/CTA ยังอยู่ด้านล่าง นี่คือเหตุผลที่ไม่ควรขยายทุกส่วนตาม artwork พร้อมกัน ขั้น layout ต้องสงวน dock แล้วคำนวณพื้นที่ body ที่เหลือ ไม่ย่อทั้งหน้าต่างหรือซ่อนคำสั่งที่ยังจำเป็น

ผลเหล่านี้ยังไม่ยืนยัน scrolling/focus ทุกเส้นทาง, สี contrast ทุกคู่, Safari/iOS, safe-area บนเครื่องจริง, font scaling, ของไม่พอ, cap หรือข้อความยาว ต้องตรวจใน prototype และก่อนนำเข้า ไม่ถือเป็น gameplay regression suite

## ข้อกำหนดส่งต่อขั้นที่ 2

ทำแบบ layout สองความสูงจาก VF01–06 ก่อน โดยโครงสร้างคือ header → identity → ขั้นตีบวก → ผลหลัก → รายละเอียดรอง → dock ค่าใช้จ่าย/ตรวจรายการ ระบุระยะ/ขนาดจริงและส่วนที่เลื่อน แสดงเส้น safe-area และพื้นที่แตะ ≥44px

กำหนดห้าสถานะ ready/review/success/insufficient/capped ในแบบถัดไป พร้อมกรณี neutral stats เป็น variant; ยังไม่ต้องสร้างหรือแก้ห้าสถานะในเกมขั้นนี้ คงกฎต้นทุน/เพดาน/ยืนยันครั้งเดียว/กลับต้นทางเดิมจากเกม ไม่เปลี่ยน save หรือ balance

หลัง layout จึงทำ token/material, decorative asset, prototype แยก, เทียบ fidelity และส่งต่อ ตามแผนย่อยเดิม ไม่เริ่มทั้งหมดในงานตรวจครั้งนี้

สำหรับหน้าดาว/สกิล/เพิ่ม Lv/เลื่อนสี/สุ่ม/ถ่ายโอน/สร้าง/รีไซเคิล/หลอมแร่ ให้นำภาษาภาพร่วมไปใช้ แต่ต้องออกแบบส่วนผลและ review ตามคำสั่งจริง: ผลสุ่มไม่ควรแสดงตัวเลขรับประกัน, donor ที่ถูกใช้หมดต้องเห็นชัด, ★5/เพดานต่างจากสถานะสำเร็จทั่วไป ดู [สเปกดาว](STAR_UPGRADE_TH.md) และ [สเปกอุปกรณ์](EQUIPMENT_DEVELOPMENT_TH.md) ประกอบก่อนออกแบบรายหน้า
