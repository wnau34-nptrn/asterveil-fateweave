# แผนปรับ UX/UI พัฒนาอุปกรณ์ สกิล และอัปดาว

วันที่: 1 พฤศจิกายน 2026 (Asia/Bangkok) · ชุดอ้างอิง ART-UI-UX-002 / PR #133

## ผลลัพธ์ที่ต้องได้

ผู้เล่นเลือกงานที่ต้องการได้ตรง เห็นว่าตัวละครหรืออุปกรณ์จะเปลี่ยนอย่างไร รู้ว่าจ่ายอะไรและเสียชิ้นไหน ตรวจรายการก่อนทำ และย้อนกลับคน/ชิ้นเดิมได้ ครอบคลุมโรงตีเหล็กครบคำสั่ง สกิล และอัปดาว ไม่เพิ่มจำนวนปุ่มให้ทุกหน้าหนาแน่นเท่ากัน

เอกสารนี้เป็นแผนพัฒนา ยังไม่ใช่การรายงานว่า UI นำเข้าแล้ว งาน runtime ทุกข้อด้านล่างยังไม่เริ่ม การเขียนแผนไม่ถือเป็นการอนุมัติข้อความ/ตัวเลขที่เครื่องมือสร้างภาพเติมมา

## ฐานที่ใช้และความสัมพันธ์กับแผนเกม

ฐานอ่านรอบแรกและสาขา artwork คือเกม `feature/fateweave-initial-prototype` ที่ `c8665fa`; ก่อนเริ่มแต่ละ PR ต้อง fetch เกมล่าสุดและเทียบความเปลี่ยนแปลงอีกครั้ง ห้ามใช้ main ซึ่งเป็นฐานเอกสาร

ตรวจแผนรวม `docs/DEVELOPMENT_PLAN_TH.md` และ handoff ล่าสุดแล้ว: W8/P01/P02 ทำแล้ว; P02-03 คนจริง/อุปกรณ์จริงยังค้าง ส่วน OD-13 วาง P09 ก่อน P04 แผน UX นี้เป็นคิวปรับหน้าจอที่เจ้าของขอเพิ่ม ไม่ใช้เป็นเหตุเริ่มเศรษฐกิจ/บัญชี/รางวัลออนไลน์แทนแผนหลัก

**ทำบนระบบปัจจุบันได้:** การนำทาง, dock, ตาราง preview, แยกใช้/มี/เหลือ, review, สถานะทำไม่ได้, รวมงานสกิล, ทางเข้าพัฒนา/อัปดาว และข้อความตรงกฎที่ใช้อยู่

**ประสานเมื่อ P04 เข้าจริง:** ตัวซ้ำ+ตราเปลี่ยนเป็นเศษกลาง/ตารางชดเชย, แหล่งแต้มย้ายจากดาวไป Lv+milestone ค่าย, ผลดาว/ขั้นสูงและราคา ห้ามเปิดด้วย UI ล่วงหน้า การทำหน้าอัปดาวปัจจุบันไม่ต้องรอ P04 แต่ข้อความ/แถววัสดุต้องเปลี่ยนตาม model ได้

**เมื่อเชื่อม P09:** ใช้คำสั่ง/ผลสำเร็จจากชั้นบัญชีและ server ที่มีจริง เพิ่ม pending/retry/error และตรวจข้อมูลล่าสุด ไม่ให้ DOM เป็นผู้ตัดสินยอดเงินหรือมอบรางวัล ไม่ต้องสร้าง backend เพื่อเริ่มปรับ UI รอบนี้

## ทดสอบและเงื่อนไขส่งมอบ

แต่ละPR runtimeต้องผ่าน typecheck/lint/unit/buildตามข้อกำหนดโปรเจกต์ และfocused browser testsที่กระทบ ปรับtestsตามพฤติกรรมที่ตั้งใจเปลี่ยน ไม่ลดassertionเพื่อให้ผ่าน ปล่อยfull browser suiteให้CIตามworkflowเดิม

ใช้ไฟล์ทดสอบที่มีแล้วเป็นฐาน:

| Lv/เลื่อนสี/สุ่ม | tests/browser/forge-phase2.spec.ts |

เพิ่มtestsที่ตรวจผลจริง: preview/cancelทำให้profileเท่าเดิม, confirmหักตรงยอดครั้งเดียว, stale-reviewไม่ใช้รายการเก่า, กลับจากจัดคลังรักษาsubjectที่ยังมี, ผลสุ่มไม่ถูกสร้างจากpreview, transferไม่เอาrefundไปจ่ายล่วงหน้า เลี่ยงsnapshotที่เพียงยืนยันว่าHTMLเหมือนimplementation

ตรวจภาพจริงที่390×844และจอสั้น390×650; regression320×568และdesktopกรอบ480pxตามกฎเดิม ภาพส่งเจ้าของ390px 1–2ภาพต่อหน้าที่เปลี่ยน ส่วนbenchmark/testจำนวนมากไม่จำเป็นต้องส่งเป็นภาพทั้งหมด Chromium emulationไม่เท่ากับiOS/มือถือจริง

เงื่อนไขก่อนรวมแต่ละชุด: ไม่มีoverflow/dockบัง/ปุ่มเล็ก, keyboardและfocusถูก, จำนวนทรัพยากรตรงผลจริง, คำอธิบายตรงruntime, requiredCIผ่าน, handoffระบุผลที่รันจริงพร้อมข้อจำกัด

## ทดลองใช้งานและตัวชี้วัด

เป้าหมายที่เสนอให้วัด ไม่ใช่ผลที่ผ่านแล้ว: จากอุปกรณ์ที่เลือกถึงreviewตีบวกไม่เกิน2taps; สกิลล็อกไปโหนดตรงตัว1tap; ผู้เล่นบอกได้ว่าLvค่ายร่วมแต่ดาวรายตัว และก่อนยืนยันระบุชิ้นที่จะหาย/ทรัพยากรที่จะใช้ได้ถูก

ใช้รอบเล็ก3–5คนตามความพร้อม ให้ทำภารกิจตีบวก เลื่อนสี ถ่ายโอน อัปดาว และติดสกิล บันทึกสำเร็จ/กดผิด/ย้อน/เวลาค้นหาพร้อมสาเหตุ เปรียบbaselineก่อนสรุปว่าดีขึ้น ไม่มีเปอร์เซ็นต์ปรับปรุงล่วงหน้า การทดสอบคนนอกต้องอยู่หลังเงื่อนไขเปิดทดสอบในOD-13; ระหว่างนั้นใช้เจ้าของ/ผู้พัฒนาทดลองภายในและบันทึกข้อจำกัด

## การปล่อยและการย้อนกลับ

เริ่มจากbranchเกมล่าสุด แยกPRตามชุด ตรวจdependencyและrequiredchecksก่อนmerge เผยแพร่ผ่านworkflowเดิมตามขอบเขตงานimplementationที่ได้รับมอบหมาย ไม่ถือว่าPRartwork #133คือPRนำเข้าทุกหน้าพร้อมกัน

แต่ละชุดพร้อมส่งเมื่อflowที่กระทบครบและกลับเข้าเมนูหลักได้ ส่วนที่ยังไม่ย้ายคงทางเข้าเดิมไว้ชั่วคราวและต้องไม่มีสองคำสั่งที่อ้างsubjectคนละชิ้น ไม่มีการบังคับเปิดทุกหน้าใหม่พร้อมกันเพียงเพื่อให้ตรงภาพรวม

เกณฑ์หยุดปล่อย: หักซ้ำ/ยอดผิด, previewเปลี่ยนsave, ของหายโดยไม่แจ้ง, กลับคนผิด, controlsถูกบัง/ใช้งานไม่ได้ ย้อนเฉพาะUI commitผ่านขั้นตอนrepoเดิม ห้ามreset/migrateเซฟเพื่อย้อนหน้าตา รายการที่commitจริงแล้วต้องยังอยู่ตามกฎเดิม ไม่ใช้rollbackเป็นการคืนเงินหรือสร้างของซ้ำ

เมื่อเสร็จแต่ละPRบันทึกbranch/PR/merge/deploy, tests, ภาพ390pxและข้อจำกัดในCODEX-TO-CLAUDE.md ตรวจPRถัดไปกับสาขาเกมล่าสุดอีกครั้ง
